# Harnesses

Claude Code, Pi and Codex CLI run over one payload, `roles/ai/files/harness/`.
Content is shared by link; policy is written once and rendered into each harness's own spelling.
What each harness cannot carry is recorded rather than approximated, because a rule that silently stops applying reads exactly like a rule that is being obeyed.

## One policy, three renderings

`policy/permissions.toml`, `policy/sandbox.toml` and `policy/hooks.toml` are the source of truth, and `lib/harnessgen` (stdlib only, found by walking up to `harness.toml`) is the only thing that reads them.
Each harness gets an emitter and an `adapters/<harness>/adapter.toml` for the knobs the neutral policy has no word for, such as a model id, which is never translated between harnesses because the ids share no namespace.

| Target | What it does |
|---|---|
| `make harness` | Render every file that differs. Claude's `settings.json` is merged key by key, since a running session writes it too; everything under `generated/` and Pi's derived files are written whole |
| `make harness-check` | Write nothing and name each drifted file or owned key |
| `make harness-apply` | Merge the policy into `~/.codex/config.toml` and install the Codex rules file. `CHECK=1` reports what is pending |
| `make harness-report` | List every policy rule a harness receives no counterpart for |

A hook reaches a harness only if its `harnesses` list in `hooks.toml` names it, and the comments there say why each one is left off where it is.
`{harness}` in a policy path expands to the checkout at render time, so a clone somewhere else needs one `make harness` before its rendered files are right.
Claude's `settings.json` cannot be written from inside a Claude session, so policy changes that reach it are rendered by hand with no session open.

## Pi

Pi is a second harness over the **same payload**, not a second copy of its content. It implements the Agent Skills standard these skills are already written to, while Kura v0.3 gives each harness an independent native view made of direct links to that payload. Shared source prevents content drift; separate roots prevent one harness's availability from depending on another harness's directory.

- **`AGENTS.md` is the shared instruction file**, symlinked from `files/harness/AGENTS.md`, because it is Claude Code's second context file and pi's only one. Tooling, code standards and git conventions live there and are agent-neutral by construction.
- **`APPEND_SYSTEM.md` is appended; a `SYSTEM.md` would replace.** Pi reads `~/.pi/agent/SYSTEM.md` as a *replacement* for its own system prompt, so the file this repo used to ship traded every instruction the harness provides for the 30 lines below it, silently and with nothing to compare against. The appended form adds to the defaults, which is why the file holds only the behaviour that has no counterpart in `AGENTS.md`. The role removes a superseded `SYSTEM.md` **symlink** left by an earlier run, since a dangling one makes the prompt depend on which run last touched it, and leaves a real file alone.
- **Global skills have two native roots.** `kura sync` derives the registry-global skill closure once, then links each skill directly into Claude Code's `~/.claude/skills/` and Pi's documented neutral root, `~/.agents/skills/`. The role's old `~/.pi/agent/skills -> ~/.claude/skills` bridge is checked for its exact target and removed; any user-owned occupant stops the play rather than being replaced. Pointing either harness at the catalog's entire `skills/` tree would still put every project-scoped and dependency-only description into every session, so the global tag remains the membership authority.
- **Project skills repeat that independent topology.** A root `kura.json` records the selected harnesses and direct skill intent. Kura creates `.claude/skills/<name>` and `.agents/skills/<name>` as separate links to the same catalog skill, derives dependencies rather than persisting them, and converges only the exact cwd or root manifests discovered below an explicit scan root. Pi never reads Claude Code's project directory.
- **`/commit` and `/pr` are real Pi aliases, not prompt lookalikes.** Pi reserves `/skill:<name>` for skill commands and otherwise treats the short Claude spellings as ordinary input. [skill-aliases](../../roles/ai/files/harness/adapters/pi/extensions/skill-aliases/README.md) registers both as extension commands and resubmits the matching explicit skill command with expansion enabled, preserving arguments and queueing it as a follow-up when the agent is busy. The expanded user message still carries Pi's `<skill name="...">` marker, so the git gate sees the same invocation whether the user typed the short or explicit spelling. Naming does not depend on that prompt being followed: commit's executor refuses a nonstandard non-default branch, while PR's executor refuses a nonstandard branch and recomputes the authoritative title before any push.
- **Provisioning names both convergence scopes explicitly.** The AI role runs `kura converge --all --root ~/Developer`, because v0.3 no longer consults Claude Code's private project registry and a bare `--all` would scan only Ansible's cwd. Claude's [SessionStart hook](../../roles/ai/files/harness/adapters/claude/settings.json) checks for `./kura.json` before running cwd-only `kura converge --quiet`; Kura treats cwd as the exact project and correctly refuses otherwise. There is deliberately no Pi `session_start` equivalent: Pi discovers `.agents/skills` before an extension could repair it, so an extension would fix only the next session.
- **The hooks are translated, not ported.** [guardrails](../../roles/ai/files/harness/adapters/pi/extensions/guardrails/README.md) maps pi's `tool_call` event onto the JSON Claude's `PreToolUse` scripts read on stdin and spawns the ones `adapters/pi/generated/hooks.json` lists, in its order. That table is rendered from `policy/hooks.toml`, the same one Claude's `settings.hooks` comes from, so the em dash count, the gated-command list, the lint budget and the cloud read-only rules stay in the tested python. It fails open everywhere, which takes deliberate care because a pi `tool_call` handler that throws **blocks** the call: an unwritable temp file would otherwise turn a gate nobody can run into a gate nobody can pass.

The native Pi view relies on one fact from Pi's own loader, exercised in [test_pi_discovery.py](../../lib/python/tests/test_pi_discovery.py) by driving `loadSkillsFromDir` in a Node subprocess: Pi follows each linked skill directory. A dangling catalog link is skipped without hiding healthy peers. Kura itself owns the stronger cross-harness contract: both native views are preflighted before a mutation, a real path or foreign link is never replaced, and a partial view is reported as drift.

**Agents deliberately keep a different provisioning path.** Kura v0.3 manages skills only. Every standalone agent in `files/harness/agents/` is global by repository convention, so Ansible links and prunes that set in `~/.claude/agents/`; `~/.pi/agent/agents -> ~/.claude/agents` remains as an agent-only bridge because `pi-subagents` reads that location and has no corresponding `~/.agents/agents` global root. Project plugins and their `.agents/agents` companions remain project-owned legacy links and are not created or pruned by the role. The frontmatter is dual-keyed, `thinking:` beside `effort:` and `disallowed_tools:` beside `disallowedTools:`, because each harness reads its own key and ignores the other's; [test_pi_dialect.py](../../lib/python/tests/test_pi_dialect.py) pins the pairs equal so the two harnesses cannot drift apart silently. Both halves of "ignores" are verified rather than assumed: Claude Code 2.1.229 validates agent frontmatter only in shadow mode (an unknown key emits `tengu_frontmatter_shadow_unknown_key` telemetry, never a refusal, and a probe agent carrying both Pi keys loads and is listed), and an earlier probe of pi-subagents' own `resolveModel` landed the seats' `model: opus` on `cursor/claude-opus-5`, which carries `opus` as a literal alias in the Cursor model list.
The current Cursor policy removes those aliases from the session registry instead of relying on `enabledModels` to constrain that resolver.
Pi-subagents treats frontmatter as authoritative, even over an explicit `Agent` model argument, which is why its built-in Explore agent remains Haiku rather than accepting a caller's Codex override.
Standalone specialist `opus` and `sonnet` pins can resolve to direct Anthropic without competing Cursor aliases.
[Seat agents](seat-plugins.md) now name Codex Sol or Terra explicitly; the [product-team bench](product-team.md) uses Sol, Terra, Composer and Sonnet by workload.
These provider-qualified agent pins trade Claude Code model portability for explicit Pi subscription routing, with no automatic agent quota fallback.
`subagents.json` enables scope checks for caller-selected models and shows the actual model in running-agent rows; frontmatter and inherited-model exceptions remain part of the package's scope policy. The one unbridged piece is the `security` advisor's `tools:` allowlist: both harnesses read that same key and the values are Claude tool names, so the advisor stays Claude-only.

- **A Cursor-backed failure only ever shows a canned reason.** `pi-cursor-sdk` (the package registering the `cursor/` provider, installed under `~/.pi/agent/npm/node_modules/` by pi's own package manager rather than vendored here) reduces every failed Cursor tool run to one of four fixed strings, `missing completion`, `aborted`, `SDK run failed`, `run ended during drain`, shown as `"<tool> did not complete"` with no message and no stack. It does carry both, but only into a maintainer debug channel gated on `PI_CURSOR_SDK_EVENT_DEBUG`, writing an `errors.jsonl` per turn (confirmed the two are connected: the call sites that set `SDK run failed` each have a companion `recordError()` call next to them). Since the package can't be patched from this repo, the fix works through the env vars it already reads: `pi_debug` and `pi_last_error` (`roles/shell/files/fish/functions/`) wrap launching pi with debug capture on and reading the latest error back, the same shell-role-owns-the-export pattern `CTX7_TELEMETRY_DISABLED` already uses for an `ai`-role concern.

**The review policy reaches pi now.** `pi-review` (in `settings.json` `packages`) appends a `REVIEW_GUIDELINES.md` to its review prompt and its rubric defers to project guidelines, so the repo root carries a relative symlink to `rules/code-review.md` and the four severities arrive intact. It only reads that file from a directory that also holds a `.pi` directory, which is why one exists at the root and holds nothing else; [code-review-policy.md](code-review-policy.md) has the detail and the reason this is not the `REVIEW.md` decision reversed.

**Setup review is shared by method, not by inventory.** `/skill:setup-review` detects pi from `PI_SESSION_ID` and delegates to `pi-staff-reviewer`; Claude Code exposes the same skill as `/setup-review` and delegates to `cc-staff-reviewer`. Both reviewers load `setup-review-mechanics` for evidence thresholds, dependency safety, proposal discipline and the P0-P2 report contract, while each owns the paths, precedence rules, current-source lookup and customization vocabulary of its harness. This avoids the old state where pi could invoke `cc-review` successfully and receive a confident audit of `~/.claude`.

### Permissions: two layers, like Claude's

Claude Code is hard to talk into a destructive command because it runs two independent layers, and its `settings.json` has a block for each. `sandbox` decides which paths and domains a subprocess can reach at the OS level. `permissions` decides whether an action is permitted at all, across 182 rules. Neither subsumes the other: the sandbox would let `git push --force` through, because force-pushing touches only paths the agent already owns, and a rule list only ever blocks what somebody enumerated.

Pi carries the same pair, from two packages and two derived files, both rendered by `harnessgen.emit_pi` from the same `policy/` Claude's blocks come from.

**`pi-sandbox` is the layer that contains.** It confines bash at the OS level through a fork of Anthropic's own `sandbox-runtime`, and applies allow/deny lists to read, write and edit directly. `files/harness/adapters/pi/sandbox.json` is its derivation, from `policy/sandbox.toml` plus the path half of `policy/permissions.toml`. [test_pi_sandbox.py](../../lib/python/tests/test_pi_sandbox.py) is its specification, and `make harness-check` names the drift. Three things it cannot carry, each silent if forgotten:

- **`excludedCommands`.** Claude runs fourteen entries outside its sandbox: twelve CLIs so they can reach their own credential stores, plus `bunx ctx7` and `npx -y ctx7`, which are there for network egress instead. pi-sandbox has no per-command exclusion, so those are confined like anything else; a read of a denied path is *prompted* rather than refused, so they still work. ctx7 is the exception, because a blocked request fails outright rather than prompting, which is why a docs question under pi can end up answered from search. Blanket-allowing their credential directories would undo the `denyRead` this repo sets deliberately.
- **`$TMPDIR`.** Only a leading `~` is expanded, so a literal `$VAR` entry matches nothing. `/var/folders` stands in for it on Darwin.
- **The line between Claude's two read layers.** Claude keeps `sandbox.filesystem` (bash subprocesses) apart from `permissions.deny` (the Read tool), so the same path can be readable by git and denied to the agent. pi has one `filesystem` block and reads it twice under different rules, so that line cannot survive the translation: `allowRead` *takes precedence over* `denyRead` for bash, which is the sandbox-runtime schema's own description of re-allowing inside a denied region, and the read tool never consults `denyRead` at all, prompting for whatever falls outside `allowRead`. So every path Claude allows bash is also a read-tool grant, and the three that Claude's `permissions.deny` also names (`~/.gitconfig`, `~/.ssh/known_hosts`, `/etc/ssl/cert.pem`) are readable in pi and refused in Claude. The CA bundle is public trust material needed for HTTPS verification, while the keys beside `known_hosts` are not re-allowed. A test pins the granted set at exactly those three so a fourth cannot arrive unnoticed. Every other `Read` deny degrades from a refusal to a prompt, the same trade `excludedCommands` makes above. Both consequences are undone by the layer below, which is the clearest thing it buys: `path_read` refuses those paths to any tool or bash token that names one, while this file's syscall-level grant keeps working for the subprocess that needs it, so `git commit` still reads `~/.gitconfig` and `cat ~/.gitconfig` no longer does.

**A linked worktree is the case where the missing `git` exclusion bites.** `git` is one of the twelve CLIs Claude runs unsandboxed, so Claude never has to think about where a repo keeps its gitdir. Under pi it is confined like anything else, and `allowWrite` grants only `.`: in a worktree created by `wt add`, the gitdir lives under the *main* checkout's `.git`, a sibling of the cwd, so `index.lock`, refs and objects all fall outside the grant. Every git command that writes then dies with `Operation not permitted`, and a write inside a bash subprocess is not prompted the way a read is, so nothing offers to grant it. This reads convincingly like a guardrail refusal and is not one: `/skill:commit` runs, `git-skill-gate.sh` allows `apply.py`, and the commit fails at `git add`. `wt add` therefore writes `<worktree>/.pi/sandbox.json` naming that repo's git common dir, which pi-sandbox unions with the global list, plus a self-naming `.pi/.gitignore` so the grant stays out of the project's history. A worktree that already exists gets the same file from `/sandbox-allow write <common dir>` answered with "Allow for this project".

One translation subtlety worth knowing: pi-sandbox runs any pattern containing `*` through `resolve()`, which anchors a relative one to the cwd. So Claude's `**/.env` would quietly stop meaning "any .env" and start meaning "an .env under this project". A leading slash restores the reach, and a test asserts no `**/` pattern survives untranslated.

**`@gotgenes/pi-permission-system` is the layer that decides.** It matches on what a command *is*, over surfaces that line up almost one for one with Claude's rule vocabulary: `bash` command patterns, `path_read` and `path_write`, `external_directory`, per-tool names, `mcp` and `skill`. `files/harness/adapters/pi/permission-system/config.json` is its derivation, from the half of `policy/permissions.toml` the sandbox could not read, and [test_pi_permissions.py](../../lib/python/tests/test_pi_permissions.py) is its specification. 98 rules cross that pi-sandbox left on the floor: 64 `Bash(...)` denies, 25 `Bash(...)` allows, the five bare tool names and the four `mcp__*` entries. The two `WebFetch`/`WebSearch` allows are dropped, because pi registers neither.

Four things about that translation are load-bearing rather than incidental. **Order is the policy**, because within one surface map the last matching pattern wins where Claude's rules are order-free and deny beats allow, so the file emits a fallback, then allows, then denies, then the two `.env.example` carve-outs that have to come after the denies they except. **A translated allow can collide with a translated deny**: `Bash(pgcli:*)` and `Bash(pgcli *)` both become the key `pgcli *`, which cannot hold two actions, so the allow is dropped and Claude's answer, deny, is what ships. **A doubled star is not a globstar here**, since one `*` already crosses separators, which is the opposite of the `/**/` the other file needs. And **writes stay silent**, because Claude sets `autoAllowBashIfSandboxed`, which is the config saying in its own words that where the sandbox confines an action it should not also ask; pi-sandbox confines `bash`, `write` and `edit` to `allowWrite` and prompts outside it, so those three surfaces are `allow` here and this layer contributes only the deny lists. Flipping `write` and `edit` to `ask` is the one-line change if literal prompt-parity is ever wanted over that reading.

**Role-owned global skill scripts are outside the project but inside the trusted harness.**
The `external_directory` surface therefore keeps its `ask` fallback and allows `~/.claude/skills/*` and `~/.agents/skills/*`, so a skill can invoke its own script through either native global root without asking on every session.
The permission package matches both the referenced and symlink-resolved forms, while pi-sandbox grants those payload trees read access but not write access, so this decision-layer exception does not make the installed skills mutable.
`piInfrastructureReadPaths` cannot carry the exception because that package knob applies only to read-only file tools and deliberately excludes bash.

The package is the only entry in `packages` carrying a version. It has shipped four breaking releases, all of them fail-closed corrections that turn a silent allow into a prompt or a block, and `pi update` skips a versioned spec, so an unattended update cannot change what the shell may run. Its config also does not live beside the others: the package expects `config.json` inside a directory named after itself, and it writes a review log holding unredacted bash command strings into that same directory, so the play creates a real directory there and links only the one file into it.

Two things bound which version the pin may name. `~/.npmrc` sets `min-release-age=7`, npm's supply-chain cooldown, so a version published in the last week cannot be resolved at all and `pi install` fails with `ETARGET` rather than anything mentioning a cooldown: pick the newest version that has aged past the window, not the registry's `latest`. And the config has to be revalidated against the version being moved to, because the package ships the schema it validates against and a rejected global scope enforces none of these rules rather than falling back to the last good one. That failure is quiet from inside the repo, since a drift test can agree with a derivation that produces a file the package will not load, so validation is part of moving the pin and not an optional check:

```bash
npx --yes ajv-cli@5 validate --spec=draft2020 --strict=false \
  -s node_modules/@gotgenes/pi-permission-system/schemas/permissions.schema.json \
  -d roles/ai/files/harness/adapters/pi/permission-system/config.json
```

**The strongest alternative was one package doing both jobs, and it was rejected on this machine's own workflow.** `pi-permission-modes` bundles an OS sandbox with a policy engine, parses bash with a real tree-sitter AST rather than wildcards, and adds Claude-style switchable modes on a keybind. It also disables its sandbox entirely in a git worktree, because bubblewrap cannot bind `.git/hooks` under a file, and `wt add` is a primary workflow here. Its value is also concentrated in TUI interactions that the Cursor bridge does not deliver, and it was six weeks stale against a host that ships weekly. `pi-verdict` is on a different axis again, routing the gray zone to a model classifier, which trades the determinism this repo derives its whole policy from for per-call latency and cost. Neither is a sandbox on its own, and neither replaces the pair.

**Pi has no third answer, so the cloud gate loses its middle tier.** A `tool_call` handler returns `{ block }` or nothing, and pi ships no permission prompt. `cloud-readonly-gate.sh` is three-tiered, and its broadest tier is an `ask` printed as JSON on stdout with exit 0, so exit status alone reports the same thing for `ask` and for `allow`: an extension checking only the code would let the whole tier through while looking like it had bridged the gate. It is read and mapped to a refusal, with the hook's own reason plus a line saying pi cannot ask. The residual is real and unfixable here: the gate documents itself as fail-closed for cloud commands while `guardrails.ts` must fail open, so a machine where the hook cannot run has cloud commands ungated in pi.

**`git-skill-gate.sh` runs on every bash call in pi and behind three matchers in Claude, and that is deliberate.** Its `main()` refuses `--no-verify` before it works out which subcommands are gated, so that refusal applies to any command at all; everything else exits 0 once `gated` is empty, so a non-git command self-guards for free. Claude's `git *`, `gh *` and `glab *` matchers therefore catch `--no-verify` only inside those three, and narrowing pi to match would **remove** protection. The cost is a `python3` spawn per bash tool call, which is a latency item to measure rather than a correctness one.

### The gates only see pi's own tools, and the cursor provider does not use them

Every hook in `guardrails.ts` hangs off pi's `bash`, `write` and `edit` tool calls.
That is the whole reach of the translation, and with the Cursor provider it reaches nothing unless the builtins are exposed.

Pi runs Cursor models through the Cursor SDK's local agent, which brings its own host tools for shell, files, grep and edits, and `pi-cursor-sdk` hides the overlapping pi builtins from its bridge unless `PI_CURSOR_EXPOSE_BUILTIN_TOOLS` is set.
A hidden builtin never produces a `tool_call`, so `git-skill-gate.sh`, `em-dash-gate.sh`, `cloud-readonly-gate.sh`, `pre-commit-verify.sh` and the rtk rewrite all go unrun, and pi-sandbox does not confine the command either.
Nothing reports this. A session where no gate ran looks precisely like a session where every command was checked and allowed, which is how it survived unnoticed: the only way to tell them apart from a transcript is that `blockResult` appends `In pi, /commit and /pr load /skill:commit and /skill:pr` to a refusal, and that string had never once been written.

It also produces a failure that looks like a gate but is not one. Cursor's own shell returns `Cursor shell did not complete / missing completion` for the commands `/commit` and `/skill:commit` need, while read-only ones return normally, and a model handed that silence in a repo full of hook source will explain it as `git-skill-gate.sh` refusing the commit. It reads as a guardrail working. It is a tool call that never finished.

`config.fish` therefore exports `PI_CURSOR_EXPOSE_BUILTIN_TOOLS=1`, which puts `pi__bash` and its siblings back on the bridge; a bridged call is real pi execution, emitting the `toolCall` the gates are hooked to.
It cannot live in `pi/settings.json`, which has no `env` block, for the same reason `guardrails.ts` passes `RTK_HOOK_AUDIT` on its own spawn.
`APPEND_SYSTEM.md` carries the matching instruction, because exposure only *offers* the bridged tools: pi's `--no-tools` and `--exclude-tools` act on pi's own registry and cannot retire Cursor's host tools, so under this provider the gates are steered rather than enforced.
That gap is what the `⌁ cursor` footer badge exists to show: it carries `⚠️ gates off` beside it whenever the exposure is missing, which is the state nobody can otherwise see, since a session where no hook ran reads exactly like one where every command passed.
The badge stands on its own in the healthy state too, which is a deliberate reversal of what it used to do.
Cursor's tool calls take a different path through the harness, so which side of that line a session is on is worth a word even when the answer is the good one, and a badge that only ever appears when something is wrong cannot be told apart from one that failed to render.

### rtk rides along with the gates, because position is the whole contract

`rtk` is the fifth `PreToolUse` entry in Claude's `settings.json`, and the only one that rewrites a command instead of refusing one.
That makes it a gate in position only, which is exactly what has to be preserved: it is **last** in Claude's hook array, after the three gates have read the command the caller actually wrote.

It therefore lives inside `guardrails.ts` rather than in an `rtk.ts` of its own.
Pi loads extensions in `readdir` order and runs every `tool_call` handler in that order, and the extension directory is not even exclusively ours (herdr installs one too), so a separate file's rewrite could land before the gates read the command.
A `git-skill-gate.sh` handed `rtk git commit` instead of `git commit` is a gate that has stopped matching, and nothing about it looks broken from outside: the extension loads, the hook runs, the command is allowed.
Inside one handler that ordering is a property of the code, and a parametrized test pins the rewrite after each of the three gates.
One exposure is left standing, and Claude has it too: another extension's handler running after this one sees the rewritten command, exactly as anything ordered after Claude's hook array does.

Three smaller differences:

- **`rtk hook claude`, not `rtk hook check`.** `check` prints the bare rewritten command and would be less code, but it is a dry run, so rtk's own audit and tee side effects never fire. Going through the target Claude goes through keeps one code path inside rtk for both harnesses. The reply is read from `hookSpecificOutput.updatedInput.command`, and exit status carries nothing: rtk exits 0 either way, and an empty stdout is the entire signal for "no rewrite".
- **`RTK_HOOK_AUDIT` moves from settings into the child env.** Claude sets it in its settings `env` block; pi's settings have no `env` block at all, so the extension passes it on the spawn. A test reads the value out of `settings.json` so the two cannot drift.
- **The footer segment mirrors `statusline.sh` rather than inventing a state.** Same glyph, same three states: nothing when `rtk` is off `PATH`, `rtk` when `RTK_ENABLE` is set, `rtk off` otherwise. A rewrite the caller cannot see is worse than no rewrite, and a second vocabulary for the same toggle across two harnesses would cost the recognition the segment exists for. `RTK_ENABLE` stays a manual per-shell export for both harnesses; nothing in the repo sets it.

Fail-open reads the other way round here than it does for the gates. Their failure mode is a refusal nobody can pass, so they allow; rtk's is a rewrite nobody asked for, so a missing, slow or unparseable rtk leaves the command exactly as written.

### What a skill's frontmatter loses

pi's skill loader reads exactly three fields from a `SKILL.md`, `name`, `description` and `disable-model-invocation`, and ignores the rest. So `allowed-tools:` and `effort:` are Claude-only, silently, on the 22 skills that carry one.

`model:` used to be in that list and no longer is. What the loader drops an extension can read for itself, and [skill-model](../../roles/ai/files/harness/adapters/pi/extensions/skill-model/README.md) does: on a `/skill:<name>` it looks the file up through `pi.getCommands()`, on a `read` of any `SKILL.md` it takes the path the model already used, then parses the frontmatter and pins the declared model for one agent run. That run is the same boundary Claude Code uses, where the override "applies for the rest of the current turn" and the session model resumes on the next prompt, so one string in one shared file means the same thing in both harnesses instead of needing a pi-only key beside it. Bare values such as `opus` are matched against `ctx.scopedModels`, which is `enabledModels` in declared order.
The configured Cursor entries are limited to `composer-2-5` and `grok-4.6`, so shared skills declaring `opus`, `sonnet` or `haiku` select direct Anthropic models instead of spending Cursor's Other Models allowance.
The user confirmed their enterprise allowance covers Anthropic API use, but that account can still hit its spend limit.
Codex Terra is the session default; basic-tier Google, Ollama Cloud and xAI models remain selectable without joining the automatic skill fallback routes.
`test_pi_skill_model.py` pins the default and the selected Cursor model set.
This list scopes skill selection and model cycling; the provider-level restriction lives in [cursor-model-policy](../../roles/ai/files/harness/adapters/pi/extensions/cursor-model-policy/README.md).
It wraps the installed Cursor provider without replacing its authentication or transport, filters its session catalog, and rejects disallowed model IDs before either stream method delegates to the SDK.
The allowlist is exact: aliases, `auto`, fast/slow selection suffixes and future models do not join it implicitly.
The policy is re-applied before agent runs, turns, model selections, compactions and tree summaries, because `/cursor-refresh-models` replaces the provider registration.
A restored session holding an old Cursor model is rejected rather than silently billed; select an allowed model to continue.
The policy applies while this extension is loaded, not to standalone Cursor clients or Cursor-native delegation inside the SDK.
The CLI catalog listing runs before session hooks and may still list models that actual sessions reject.
[Cursor's pricing documentation](https://cursor.com/docs/models-and-pricing) separates Cursor Models from Other Models, but Composer and Grok can still incur on-demand usage after their pool is exhausted.
Disable on-demand usage in the Cursor account to enforce the billing boundary; local model selection alone cannot do that.

[model-routing.json](../../roles/ai/files/harness/adapters/pi/model-routing.json) owns both the Cursor allowlist and the skill redirect/fallback map.
Legacy Cursor Claude skill pins redirect to direct Anthropic before lookup, even when the forbidden Cursor source is absent from the catalog.
Cursor GPT pins redirect immediately to their matching Codex models; Fable pins use direct Anthropic Opus.
This keeps tracked skills such as `unslop` working without editing content that Kura can replace.
Project-owned plugin skills now declare their direct targets instead of depending on legacy redirects.
After redirection, Opus falls back to Codex Sol, Sonnet to Terra, Haiku and Composer to Luna, and Grok 4.6 to Terra.
If a routed primary is absent or has no configured auth, the skill starts directly on its fallback.
The same account-error routes are armed for unpinned agent runs, and pi-subagents binds this repository-owned extension inside its child sessions, so the built-in Explore agent can retry Haiku failures on Luna without patching the package.
The selected model and thinking level are restored when the run settles, so the next run starts from its configured primary again.

The local assignments keep the largest Codex model for research, planning and agent audits, Terra for the default session, Luna for handoffs, Composer for commit/PR/Jira/Cloudflare/product-lead workflows, Sonnet for CodeRabbit fixes, acceptance criteria and prose cleanup, and Opus for agent authoring.
Unpinned skills inherit the session model.
If a pinned skill's turn returns an authentication, subscription, quota, spend-limit or rate-limit error, the extension switches to the fallback and rewrites that failed assistant response into pi's retryable provider form; pi then removes the failed response from live context and repeats that assistant turn on the fallback. Network, server and generic SDK errors stay on pi's normal provider retry path. An unmapped model has no fallback. The fallback depends on pi's default-enabled agent retry, and deliberately restores the pre-skill session model when the run settles so the next skill invocation tries its source model first again.

A value outside that route that resolves to nothing, or resolves to a provider with no auth, warns and leaves the session where it was. The pin's prior model and thinking level go into a session entry rather than a closure, because pi restores the pinned model on resume and a closure would have nothing left to put back. While a pin is live the footer carries a `<skill> on <model>` segment through `setStatus`: the model segment above already shows *which* model is active, and the one thing it cannot show is that a skill is the reason, so this duplicates no reading of pi's own numbers.

The consequence worth stating is the first: a skill Claude Code restricts to a handful of tools runs with pi's full tool set. Enforcing it in `guardrails.ts` was designed and rejected, because the values are Claude permission specifiers with argument patterns (`Bash(git status *)`) and 17 of the 20 skills carrying the key qualify their Bash, so a tool-name-level gate would have allowed an unrestricted shell for those 17 while reading like enforcement. The sandbox config above covers that surface properly, by confining what any command may touch rather than which skill may run it. `test_pi_dialect.py` freezes the set so the limitation cannot quietly widen, and refuses a `thinking:` on a skill, which would read as a pin pi honours and is not one.

Agents are the opposite case and are dual-keyed, because `pi-subagents` does read agent frontmatter. The invariant is `effort:` rather than a filename: every agent pinning a depth for Claude pins the same one for pi. That check used to glob `*-staff-engineer.md` and then drop any file carrying `tools:`, which hid eight agents twice over, and the `tools:` half was the subtler error, since a Claude-only tool allowlist says nothing about how deep a seat thinks.

### Trust is two stores, and they cannot be unified

`kura trust` reads and writes the selected installed harnesses as one preflighted transaction. Pi keeps `~/.pi/agent/trust.json`, a flat `{path: bool}` map guarded by `proper-lockfile`, and three of its derivations differ:

- **The key is the cwd**, not the git repo root, so a subdirectory is its own workspace where Claude Code would have keyed the whole repo.
- **The key is realpathed**, where Claude Code's deliberately is not, so a path reached through a symlink yields different keys in the two stores.
- **The nearest entry wins, including a refusal.** Claude Code's gate walks past a `false` looking for a `true`; pi stops at the first boolean, so a denial on a parent shadows a grant above it.

This matters because a selected Pi view gives the project a `.agents/skills` directory, and Pi treats that directory as a reason to ask. `converge --all` can therefore arm the prompt in every initialized project it repairs. `kura trust --on` records the native Claude and Pi decisions for the exact initialized cwd; `defaultProjectTrust: "always"` is deliberately not set because Pi's trust also gates project extensions, and blanket-trusting every directory to silence a prompt of our own making is the wrong trade.

`claude-ui`, `velocity` and `statusline` are the display half, and they answer three different questions.

`claude-ui` is parked: its documented directory is omitted from `PI_EXTENSIONS`, so the role does not link it into Pi's auto-discovery directory. Adding it to that manifest is the whole re-enable. What it does when loaded: it makes the conversation read like Claude Code without touching Pi internals or replacing the selected theme. The editor and rendered user prompts carry Claude's `❯` caret, assistant text carries Claude's `⏺` bullet, and the working row uses Claude's star animation with present-tense language, target paths and elapsed time. It re-registers only built-in tool definitions with semantic sibling `⏺` calls and `⎿` result children. The default view gives source, search, and directory results their first ten lines, shell results their final twenty lines, and edit diffs their first thirty lines; `Ctrl+O` reveals all detail returned by Pi. Errors remain fully visible. Native thinking is hidden by default behind the static `✻ Thinking…` label, and `Ctrl+T` reveals the original content. An earlier version appended a durable `Thought for Ns` entry per thinking block, but on a model that interleaves reasoning between every text block and tool call, Pi splices each entry ahead of the still-streaming assistant message that produced it (`interactive-mode.js:2920-2925`), so a turn rendered as a clump of duration rows above an undifferentiated wall of text rather than markers in place. Pi's own inline label, one per run of thinking blocks, sits in the right place already; the fix was to stop overriding it. Package tools keep their own renderers, and all colours are semantic Pi theme tokens rather than a Solarized palette.

`velocity.ts` stays **one segment**: it counts the `+` and `-` lines of the unified `patch` pi reports for each applied edit, never a diff computed here, because `edits[].oldText` is matched against the original file rather than against the result of earlier edits in the same call, so summing the halves of an `edits` array is a different number from what `git diff` reports. A `write` is counted as additions only and that is a known understatement: the event fires after the file is written, so the content it replaced is already gone.

`statusline.ts` **replaces pi's footer outright**, through `ctx.ui.setFooter`, and that is the trade worth stating because the cheaper option was available and was rejected. Pi's own footer already carries the model, provider, thinking level, context percentage, cache hit rate, cwd with branch and session cost; what it carries none of is the *reading* Claude's `statusline.sh` does for those numbers. `36.4%/200k` is a fact, and `context [▓▓▓░░░░░] 73k (36%) handoff` is the same fact with the wrap-up threshold from [context hygiene](context-hygiene.md) applied to it. Adding a second `setStatus` segment would have been upgrade-proof and would have printed a second context reading two columns from pi's own, and two disagreeing renderings of one number is worse than either.

The cost of owning the footer is paid in `statusline.ts`: the token totals, the cache hit rate and the session-versus-turn cost split are its own arithmetic over pi's session entries, so a pi release that renames a field changes those numbers silently. `lib/python/tests/test_pi_statusline.py` is the guard, checking every field the file reads against pi's own `.d.ts` and running the segments for real. Two of pi's markers are deliberately not rebuilt, because the extension API does not reach them: `(auto)` for auto-compaction and `(sub)` for a subscription-backed provider both read private session state, so a cursor session shows its token counts with no dollar figure rather than a `$0.000` it cannot justify.

Two rules hold the layout together. Segments are admitted in priority order until the width runs out rather than assembled and trimmed, so a narrow terminal keeps the context gauge and the model and loses the node version, instead of losing a whole row to one wide segment that did not fit either. And `getExtensionStatuses()` is rendered verbatim, which is what keeps `velocity.ts`, the rtk toggle, the cursor badge and any status set by the packages in `settings.json` on screen: replacing the footer without rendering that map is how a custom footer silently deletes every other extension's output.

**The values the two harnesses agree on live in `roles/ai/files/harness/statusline.json`, not in either of them.** The wrap-up threshold, the gauge cells, the lockfile table and the segment glyphs were typed into both `statusline.sh` and `statusline.ts`, and the threshold into `context-nudge.sh` as well, which is how a nudge that fires at one percentage and a gauge that marks another ship together. All five read the file now, each resolving its own realpath the way `guardrails.ts` already resolves one to find the hooks it drives, since every one of them is reached through a symlink and only the link's target has the file as a sibling. Reading it rather than importing a shared module is forced: pi loads an extension through that symlink and jiti resolves a relative import from the link rather than from its realpath, so a shared `.ts` two directories up is looked for inside `~/.pi/agent/extensions` and never found. Nothing is defaulted, because a copy of every value kept as a fallback would be the duplication the file exists to remove, and the file can only be missing when the checkout is. Each reader degrades on its own instead: no glyph renders no glyph, no threshold renders no marker. What stays duplicated is deliberate and separately pinned: the colour ramps differ because pi themes are user-authored, and pi's token format matches pi's own footer rather than Claude's.

One constraint applies to every extension here and was found the hard way in this one: **pi strips types rather than compiling them**, so TypeScript that has to be emitted instead of erased is a load error rather than a type error. A constructor parameter property (`constructor(private readonly ctx: X)`) is ordinary TypeScript, is what an editor suggests, and takes the whole extension down at startup.

`tokencost --pi` prices pi work off `~/.pi/agent/sessions/`, and the reader is separate from the Claude one because **pi records the cost itself**. So the rate table is not consulted at all, which is the whole point: a subscription or local model costs what pi says it cost, where the table would have billed it at its default tier and called every local model the dearest on the machine. Buckets are `provider/model` rather than skills, since the same model id under two providers at two prices is the comparison a multi-model setup exists to make, and folding them by id would hide it. A recorded zero is a price and a missing one is a gap, so the two are distinguished rather than both read as falsey, and an unpriced response is counted and named instead of guessed at. Compactions and branch summaries carry their own usage in pi, unlike Claude's boundary record, so they are real spend under a bucket named for the act.

## Codex

Codex reads the neutral `AGENTS.md` through `~/.codex/AGENTS.md` and global skills from `~/.agents/skills/`.
It is not a kura harness: that root exists because kura's `pi` harness writes it, so Codex's skills depend on Pi staying enabled in kura's machine config.

**`config.toml` is merged, never linked.** Codex and the ChatGPT app both write `~/.codex/config.toml` (projects, plugins, MCP servers, hook trust), so `harness-build apply codex` replaces only the keys it owns: the adapter's `[config]` table plus `sandbox_workspace_write` rendered from `policy/sandbox.toml`.
Every other key is read and written back unchanged, the first write keeps the untouched file beside it as `config.toml.harness-bak`, and a new file is created owner-only.
The stdlib reads TOML but cannot write it, so `harnessgen.tomlw` writes back what `tomllib` read, and comments in the file do not survive a write that changes something.
The role runs `apply` on every play, and a run with nothing to change writes nothing.

**The rules file is a copy.** Codex's rules loader checks `is_file()` on each directory entry and so skips a symlinked `.rules`, and Codex appends its own approvals to `~/.codex/rules/default.rules`, which a linked directory would land in this checkout.
`apply` therefore writes `~/.codex/rules/dotfiles.rules` as a real file, and `make harness-apply CHECK=1` reports it once it goes stale.

**Only a token prefix translates.** execpolicy's `prefix_rule` matches exact leading tokens and has no glob, so `git push --force *` becomes a forbidden `["git", "push", "--force"]`, while a deny with a wildcard inside a token has no rule at all.
A deny without a trailing `*` becomes a prefix too, which only widens the refusal.
Path rules, MCP and tool denies, the domain allowlist, the read lists and the write roots Codex would misread (`.` resolves against `~/.codex`, and a `$VAR` is taken literally) have no counterpart either; `make harness-report` names every one.
The command allows are left out on purpose: under `approval_policy = "on-request"` a command that stays inside the `workspace-write` sandbox is never prompted for, so an allow would spare nothing.
`codex execpolicy check --rules ~/.codex/rules/dotfiles.rules -- git push --force origin x` is the quick proof that the installed file is the one Codex obeys.

**The network is off, and that is what gates the cloud.** Codex's sandbox has no domain allowlist, only `network_access`, so it stays `false` and a command that needs the network asks to leave the sandbox.
That matters for `cloud-readonly-gate.sh`, because Codex has no `ask` answer for a hook: `permissionDecision: "ask"` is unsupported and fails open, so the gate's broadest tier only refuses in Claude and Pi, and in Codex the escalation prompt is what stands in for it.

**Hooks are linked, rendered, and trusted by hand.** `~/.codex/hooks.json` links `adapters/codex/generated/hooks.json`, which lists the scripts under `~/.codex/hooks/` for `^Bash$` (Codex matches a regex, so a bare `Bash` would match any tool containing it).
Codex runs a hook only after it is trusted in `/hooks`, once per machine.
The trust hash covers the event, matcher, command and timeout but not the script, so editing a hook script needs no re-trust and changing its manifest entry does.
Only `cloud-readonly-gate` and `pre-commit-verify` are listed. `git-skill-gate` looks for the authorising skill in a transcript field Codex never writes, so it would refuse every commit. A Codex edit arrives as an `apply_patch` payload `em-dash-gate` does not parse. rtk answers in Claude's rewrite output, which Codex has not been checked against.
So under Codex the `/commit` and `/pr` route and the em dash rule are instructions, not gates.
