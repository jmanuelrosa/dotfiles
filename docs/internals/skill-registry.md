# Skill registry & dependencies


Skills are tracked in [roles/ai/files/claude/skill-registry.json](../../roles/ai/files/claude/skill-registry.json): `repos` (synced from upstream GitHub repos) and `local_skills` (authored here). A skill entry may declare `dependencies: [<name>, ...]` — other skills it invokes at runtime (e.g. the dispatcher `grill-me` runs `/grilling`, so it depends on `grilling`). Each named dependency must itself be a registered or on-disk skill.

`claude-kit add` resolves a skill's transitive dependency closure, downloading and symlinking each into the project, and `claude-kit list` annotates it `(needs: …)`. `claude-kit sync` links the `global`-tagged skills plus one level of their declared dependencies into `~/.claude/skills/`, so a global dispatcher skill never ships without the skills it calls. Declare dependencies in the registry, not in `SKILL.md` prose — the latter is overwritten on every `claude-kit update --type skill`.

A skill that exists *only* to satisfy another skill's `dependencies` (e.g. `grilling`, `domain-modeling`) carries `dependency_only: true`. It stays a normal tracked entry — synced by `update`/`outdated` and pulled automatically when the skill that needs it is added — but every browsing surface (`claude-kit list`, `list --group`, `add --group`, `scout`, the Television picker) hides it and `claude-kit add <name>` refuses it directly, pointing the user at the parent skill. `cat.visible` is the one implementation of that hiding, and the Television picker inherits it by reading `claude-kit list --json` rather than filtering the registry itself. Resolution paths keep using the unfiltered set, or a dependency could never be installed.

Agent entries in [roles/ai/files/claude/agent-registry.json](../../roles/ai/files/claude/agent-registry.json) may also declare `dependencies` — naming **skills** (not agents) the agent invokes at runtime (e.g. `architect` depends on `planning-and-task-breakdown`). Two paths honour it: [scope.global_set](../../roles/ai/files/scripts/claude-kit/claude_kit/scope.py) folds each global agent's skills (plus one level of those skills' own deps) into the set `claude-kit sync` links, and `claude-kit add <agent> --type agent` installs each declared skill's transitive closure into the project — resolving past the `dependency_only` direct-add refusal, so an agent may depend on a skill like `domain-modeling`. `claude-kit list --type agent` carries the same `(needs: …)` annotations.

**A name must mean one artifact.** `skill-registry.json`, `agent-registry.json` and `plugins/` share a single namespace, because `claude-kit add <name>` infers the type from the name alone. A collision is not a naming annoyance, it is a silent mis-install: skills and plugins share the `.claude/skills/` leaf, so the wrong one lands at the right-looking path and the command still reports success. `duplicate_names` over the real catalog is asserted empty in [test_catalog.py](../../roles/ai/files/scripts/claude-kit/tests/test_catalog.py), so a colliding entry fails CI before it ships. The CLI still refuses rather than guessing at runtime, since a `claude-kit update --type skill` can pull an upstream skill whose name we do not control: it exits 8 listing the qualified commands, and `claude-kit add <name> --type skill|agent|plugin` picks one. `--type` applies to every name in the call. Dependencies never need it: every dependency edge (a skill's `dependencies`, an agent's `dependencies`, a plugin's `skillDependencies`) names a **skill**, and the resolver looks one up by type.

Each entry also carries `groups` — a **flat** array of tags drawn from a controlled, multi-facet vocabulary. The tooling treats it as an opaque tag set (`claude-kit list --group <tag>`, `add --group`, `remove --group`, and the Television picker all filter by membership), so adding a tag needs no code change. Tag in this order, deduped: **discipline** (exactly one — `engineering` · `quality` · `product` · `marketing` · `productivity`), then **profile/persona** (`frontend` · `backend` · `mobile` · `ios` · `desktop` · `devops` · `qa` · `security` · `designer` · `marketer` · `pm` · `writer`), then **technology** (`react` · `react-native` · `react-router` · `expo` · `swift` · `electron` · `tauri` · `node` · `nestjs` · `fastify` · `hono` · `graphql` · `apollo` · `prisma` · `tailwind` · `astro` · `tanstack` · `playwright` · `sentry` · `typescript`), then **topic/activity** (`ui` · `testing` · `review` · `refactoring` · `performance` · `architecture` · `seo` · `conversion` · `copywriting` · `writing` · `ci` · `deployment` · `observability` · `workflow` · `documentation` · `planning` · `git` · `language` · `ai` · `web` · `data` · `database` · `learning`). Reuse an existing tag before coining a new one. There is deliberately no `design` topic tag: it was a synonym of `ui` whose only holder also carried `ui`, while the `designer` persona already returns the whole family (`frontend-design`, `emil-design-eng`, `ux-shaper`, the `design` seat), so two tags meant one browsing surface silently returned an incomplete set. `agent-registry.json` uses the same `groups` shape but a simpler vocabulary.

**A technology tag is a claim `scout` must be able to check.** The tooling treats tags as opaque everywhere except one place: [fingerprint.TECH_TAGS](../../roles/ai/files/scripts/claude-kit/claude_kit/fingerprint.py) gates recommendations, and `rank()` satisfies that gate from **direct** evidence only. So a technology tag needs a probe that can detect it — a dependency in `package.json`, a marker file — or every artifact carrying it is dropped from every project, silently and for ever, while `claude-kit list` still shows it. This is why the technology facet above is shorter than it looks like it should be: `swiftui` is gone because nothing can detect SwiftUI specifically (`swift` and `ios` cover that ground), and `react-router` joined it because a probe existed for a tag the vocabulary had never listed. Two corollaries: a declared dependency names **both** its own technology and the platform it implies, since `expo` ⇒ `mobile` and `fastify` ⇒ `node` are facts rather than guesses; and an `IMPLIED_TAGS` entry pointing at a gate tag is inert, which is what once made a Fastify project the only kind of Node project that never saw the `node` skill. `test_scout.py`'s G1 to G3 assert all of this, so a tag added without an emitter fails CI rather than going quiet.

One tag sits outside those capability facets: `global` is a **scope** marker, appended last. It flags the entries `claude-kit sync` links into `~/.claude/skills/` and `~/.claude/agents/` so they are available in every project without a per-project `add`. This tag is the single source of truth for that set: `scope.global_set` derives it from `groups` membership (there is no hand-maintained list, in `defaults/main.yml` or anywhere else), then expands the skills by their declared dependencies as described above. Tag an entry `global` to add it to the set. The Television skill and agent pickers expose a **No global** source (in `claude-skills.toml` / `claude-agents.toml`, backed by the `noglobal` filter in `_tv_claude_list.fish`) that hides entries already installed everywhere, so browsing to install into a specific project shows only what is not.

**The tag decides *location*, not just membership.** A global artifact belongs **only** in `~/.claude/` and everything else **only** in a project, which is why a project-scoped install refuses when there is no project: running from `$HOME` used to write into `~/.claude/` silently, and that is how a non-global `idea-refine` ended up auto-firing in every repo. In claude-kit the rule is `--global` plus `NO_PROJECT`, above. `scope.global_set` is the **only** implementation of the membership half of it (tag **plus one level of declared dependencies**, so `grilling` and `jira` count as global even though neither carries the tag): the Television picker used to restate it in fish, and now reads it off `claude-kit list --json` like every other fact on a row.

Because that invariant holds, `~/.claude/skills/` and `~/.claude/agents/` are role-owned and `claude-kit sync` **prunes** them on every `make run-role ROLE=ai`: any symlink resolving into `files/claude/` that is not in the derived set is deleted. Unlike the Ansible block it replaced, this now includes `files/claude/plugins/`, so a seat plugin linked into `~/.claude/skills/` is pruned unless it is tagged `global` (none is today); a plugin is still never mistaken for a stale *skill*, because the store the link resolves into decides its type. A real directory is never a candidate. Removing a global link by hand is a transient override, since the next run restores it; to drop one for good, remove its `global` tag.
