# Skill registry & dependencies


Skills are tracked in [roles/ai/files/harness/kura/catalog/skill-registry.json](../../roles/ai/files/harness/kura/catalog/skill-registry.json): `upstream`, keyed by GitHub `owner/repo`, whose entries each carry a `branch` and the `skills` synced from it by `upstream_path`, and `local`, the skills authored here. A skill entry may declare `dependencies: [<name>, ...]` — other skills it invokes at runtime (e.g. the dispatcher `grill-me` runs `/grilling`, so it depends on `grilling`). Each named dependency must itself be a registered or on-disk skill.

`kura add` resolves a skill's transitive dependency closure, downloading and symlinking each into the project, and `kura list` annotates it `(needs: …)`. `kura sync` links the skills with `global: true` plus their declared dependencies, recursively, into `~/.claude/skills/` and `~/.agents/skills/`, so a global dispatcher skill never ships without the skills it calls. Declare dependencies in the registry, not in `SKILL.md` prose — the latter is overwritten on every `kura update --type skill`.

A skill that exists *only* to satisfy another skill's `dependencies` (e.g. `grilling`, `domain-modeling`) carries `dependency_only: true`. It stays a normal tracked entry — synced by `update`/`outdated` and pulled automatically when the skill that needs it is added — but every browsing surface (`kura list`, `list --group`, `add --group`, `scout`, the Television picker) hides it and `kura add <name>` refuses it directly, pointing the user at the parent skill. `cat.visible` is the one implementation of that hiding, and the Television picker inherits it by reading `kura list --json` rather than filtering the registry itself. Resolution paths keep using the unfiltered set, or a dependency could never be installed. In Claude Code, harnessgen renders every `dependency_only` skill into `skillOverrides` as `name-only`: Claude no longer sees its description, so it is not picked up on its own, while the parent can still load it by name. Any other per-skill visibility goes in `[skill_overrides]` in the Claude adapter, never in an upstream `SKILL.md`.

Agent entries in [roles/ai/files/harness/kura/catalog/agent-registry.json](../../roles/ai/files/harness/kura/catalog/agent-registry.json) use `upstream` and `local` like the skill registry. Kura projects standalone agents with `global: true` and their declared skill dependencies into both harnesses with bare `kura sync`; `kura sync --type skill` leaves agent views unchanged. The AI role removes its old agent links, but never runs sync automatically.

Bundle entries in [bundle-registry.json](../../roles/ai/files/harness/kura/catalog/bundle-registry.json) register each bundle by `name` and carry descriptive `groups` for filtering, grouping, and project selection.
Kura v0.9.0 reads groups from local and upstream registry rows; they are not inherited by bundle-owned agents or skills.
Kura still rejects `global`, `dependencies`, and `dependency_only` on bundle rows, including `global: false`, and refuses the retired `global` group tag.
Bundle manifests keep `name`, `description`, `version`, `author`, and optional `requires`; groups and scope stay out of the manifest.
All shipped bundles remain project-scoped.
The [migration plan](../plans/2026-10-06-bundle-registry-metadata.md) records the restored historical groups and compatible executable.

**A name still means one artifact across this repository.** `skill-registry.json`, `agent-registry.json`, and `kura/catalog/bundles/` keep a shared namespace. A bundle name must not collide with a registered skill or agent. Dependencies in registries and in `bundle.json` `requires` continue to name skills.

Each entry also carries `groups` — a **flat** array of tags drawn from a controlled, multi-facet vocabulary. The tooling treats it as an opaque tag set (`kura list --group <tag>`, `add --group`, `remove --group`, and the Television picker all filter by membership), so adding a tag needs no code change. Tag in this order, deduped: **discipline** (exactly one — `engineering` · `quality` · `product` · `marketing` · `productivity`), then **profile/persona** (`frontend` · `backend` · `mobile` · `ios` · `desktop` · `devops` · `qa` · `security` · `designer` · `marketer` · `pm` · `writer`), then **technology** (`react` · `react-native` · `react-router` · `expo` · `swift` · `electron` · `tauri` · `node` · `nestjs` · `fastify` · `hono` · `graphql` · `apollo` · `prisma` · `tailwind` · `astro` · `tanstack` · `playwright` · `sentry` · `typescript`), then **topic/activity** (`ui` · `testing` · `review` · `refactoring` · `performance` · `architecture` · `seo` · `conversion` · `copywriting` · `writing` · `ci` · `deployment` · `observability` · `workflow` · `documentation` · `planning` · `git` · `language` · `ai` · `web` · `data` · `database` · `learning`). Reuse an existing tag before coining a new one. There is deliberately no `design` topic tag: it was a synonym of `ui` whose only holder also carried `ui`, while the `designer` persona already returns the whole family (`frontend-design`, `emil-design-eng`, `ux-shaper`, the `design` seat), so two tags meant one browsing surface silently returned an incomplete set. `agent-registry.json` uses the same `groups` shape but a simpler vocabulary.

**A technology tag is a claim `scout` must be able to check.** The tooling treats tags as opaque everywhere except one place: kura's `fingerprint.TECH_TAGS` gates recommendations, and `rank()` satisfies that gate from **direct** evidence only. So a technology tag needs a probe that can detect it — a dependency in `package.json`, a marker file — or every artifact carrying it is dropped from every project, silently and for ever, while `kura list` still shows it. This is why the technology facet above is shorter than it looks like it should be: `swiftui` is gone because nothing can detect SwiftUI specifically (`swift` and `ios` cover that ground), and `react-router` joined it because a probe existed for a tag the vocabulary had never listed. Two corollaries: a declared dependency names **both** its own technology and the platform it implies, since `expo` ⇒ `mobile` and `fastify` ⇒ `node` are facts rather than guesses; and an `IMPLIED_TAGS` entry pointing at a gate tag is inert, which is what once made a Fastify project the only kind of Node project that never saw the `node` skill. kura's `test_scout.py` asserts all of this in its G1 to G3, in that repository rather than here, so a tag added without an emitter fails there rather than going quiet.

`global` is an optional **boolean root policy**, separate from descriptive `groups`, on skills and standalone agents.
Only `global: true` selects a root; omission or `false` does not, but its skills can still install globally through another root's dependency closure.
The retired `global` group tag is rejected even when the flag is also present; `--group global` is no longer a global-policy selector.
On a skill the flag tells `kura sync` to project that skill and its recursive skill dependencies into both enabled native global roots, `~/.claude/skills/` and `~/.agents/skills/`.
There is no hand-maintained skill list in `defaults/main.yml`.
On a standalone agent it tells Kura to link that agent and its required skills into `~/.claude/agents/` and `~/.pi/agent/agents/`.
Both are real directories, not links into this repository.

**The flag decides location, not just membership.** A global skill belongs in both machine roots and a non-global skill belongs in every native root selected by the project's root `kura.json`. Project commands use the exact cwd and refuse without initialization, so running from `$HOME` cannot silently turn project intent into global state. A direct project skill that later becomes global stays declared in `kura.json`; convergence removes its redundant project links only after the global views are healthy, and restores them if policy later changes.

**Upgrade before mutating views.** The pinned Kura v0.9.0 supports bundle registry groups, explicit global flags for skills and standalone agents, and all three registry schemas.
Run `make run-role ROLE=ai` to install it before running `sync`, `converge`, or other catalog mutations; Kura v0.7.0 ignores the flags and v0.8.0 rejects bundle groups.
Registry `version: 3` does not negotiate compatibility, and the executable does not migrate registries automatically.

Kura owns and safely prunes catalog-backed links under `~/.claude/skills/`, `~/.agents/skills/`, `~/.claude/agents/`, and `~/.pi/agent/agents/`. The role removes only its own former agent links; bundle content lives under `files/harness/kura/catalog/bundles/` and is installed with `kura add --type bundle`.
