# Skill registry & dependencies


Skills are tracked in [roles/ai/files/harness/kura/catalog/skill-registry.json](../../roles/ai/files/harness/kura/catalog/skill-registry.json): `upstream`, keyed by GitHub `owner/repo`, whose entries each carry a `branch` and the `skills` synced from it by `upstream_path`, and `local`, the skills authored here. A skill entry may declare `dependencies: [<name>, ...]` — other skills it invokes at runtime (e.g. the dispatcher `grill-me` runs `/grilling`, so it depends on `grilling`). Each named dependency must itself be a registered or on-disk skill.

`kura add` resolves a skill's transitive dependency closure, downloading and symlinking each into the project, and `kura list` annotates it `(needs: …)`. `kura sync` links the `global`-tagged skills plus their declared dependencies, recursively, into `~/.claude/skills/` and `~/.agents/skills/`, so a global dispatcher skill never ships without the skills it calls. Declare dependencies in the registry, not in `SKILL.md` prose — the latter is overwritten on every `kura update --type skill`.

A skill that exists *only* to satisfy another skill's `dependencies` (e.g. `grilling`, `domain-modeling`) carries `dependency_only: true`. It stays a normal tracked entry — synced by `update`/`outdated` and pulled automatically when the skill that needs it is added — but every browsing surface (`kura list`, `list --group`, `add --group`, `scout`, the Television picker) hides it and `kura add <name>` refuses it directly, pointing the user at the parent skill. `cat.visible` is the one implementation of that hiding, and the Television picker inherits it by reading `kura list --json` rather than filtering the registry itself. Resolution paths keep using the unfiltered set, or a dependency could never be installed.

Agent entries in [roles/ai/files/harness/agent-registry.json](../../roles/ai/files/harness/agent-registry.json) may still declare `dependencies` naming skills the agent invokes at runtime, but Kura v0.3 manages skills only and does not read that registry. The AI role provisions every standalone agent globally. Any skill such an agent requires globally must therefore carry its own `global` tag in `skill-registry.json`; `planning-and-task-breakdown` and `documentation-and-adrs` do so for `architect`, while dependencies already reached through a global skill need no duplicate tag.

**A name still means one artifact across this repository.** `skill-registry.json`, `agent-registry.json` and `plugins/` keep a shared namespace even though Kura v0.3 accepts only `--type skill`. Skills and plugins both occupy Claude Code's `skills/` leaf when project-owned legacy links are present, so a collision remains ambiguous to humans and to any later agent/plugin manager. Dependencies in every registry or plugin manifest continue to name skills.

Each entry also carries `groups` — a **flat** array of tags drawn from a controlled, multi-facet vocabulary. The tooling treats it as an opaque tag set (`kura list --group <tag>`, `add --group`, `remove --group`, and the Television picker all filter by membership), so adding a tag needs no code change. Tag in this order, deduped: **discipline** (exactly one — `engineering` · `quality` · `product` · `marketing` · `productivity`), then **profile/persona** (`frontend` · `backend` · `mobile` · `ios` · `desktop` · `devops` · `qa` · `security` · `designer` · `marketer` · `pm` · `writer`), then **technology** (`react` · `react-native` · `react-router` · `expo` · `swift` · `electron` · `tauri` · `node` · `nestjs` · `fastify` · `hono` · `graphql` · `apollo` · `prisma` · `tailwind` · `astro` · `tanstack` · `playwright` · `sentry` · `typescript`), then **topic/activity** (`ui` · `testing` · `review` · `refactoring` · `performance` · `architecture` · `seo` · `conversion` · `copywriting` · `writing` · `ci` · `deployment` · `observability` · `workflow` · `documentation` · `planning` · `git` · `language` · `ai` · `web` · `data` · `database` · `learning`). Reuse an existing tag before coining a new one. There is deliberately no `design` topic tag: it was a synonym of `ui` whose only holder also carried `ui`, while the `designer` persona already returns the whole family (`frontend-design`, `emil-design-eng`, `ux-shaper`, the `design` seat), so two tags meant one browsing surface silently returned an incomplete set. `agent-registry.json` uses the same `groups` shape but a simpler vocabulary.

**A technology tag is a claim `scout` must be able to check.** The tooling treats tags as opaque everywhere except one place: kura's `fingerprint.TECH_TAGS` gates recommendations, and `rank()` satisfies that gate from **direct** evidence only. So a technology tag needs a probe that can detect it — a dependency in `package.json`, a marker file — or every artifact carrying it is dropped from every project, silently and for ever, while `kura list` still shows it. This is why the technology facet above is shorter than it looks like it should be: `swiftui` is gone because nothing can detect SwiftUI specifically (`swift` and `ios` cover that ground), and `react-router` joined it because a probe existed for a tag the vocabulary had never listed. Two corollaries: a declared dependency names **both** its own technology and the platform it implies, since `expo` ⇒ `mobile` and `fastify` ⇒ `node` are facts rather than guesses; and an `IMPLIED_TAGS` entry pointing at a gate tag is inert, which is what once made a Fastify project the only kind of Node project that never saw the `node` skill. kura's `test_scout.py` asserts all of this in its G1 to G3, in that repository rather than here, so a tag added without an emitter fails there rather than going quiet.

One tag sits outside those capability facets: `global` is a **scope** marker, appended last. On a skill it tells `kura sync` to project that skill and its recursive skill dependencies into both enabled native global roots, `~/.claude/skills/` and `~/.agents/skills/`. There is no hand-maintained skill list in `defaults/main.yml`. On a standalone agent the tag records the repository convention that every such agent is global; Ansible, not Kura, links that whole directory into `~/.claude/agents/` and Pi reaches it through the agent-only bridge at `~/.pi/agent/agents`.

**The tag decides location, not just membership.** A global skill belongs in both machine roots and a non-global skill belongs in every native root selected by the project's root `kura.json`. Project commands use the exact cwd and refuse without initialization, so running from `$HOME` cannot silently turn project intent into global state. A direct project skill that later becomes global stays declared in `kura.json`; convergence removes its redundant project links only after the global views are healthy, and restores them if policy later changes.

Kura owns and safely prunes catalog-backed links under `~/.claude/skills/` and `~/.agents/skills/`. Ansible separately owns links under `~/.claude/agents/`. Project plugin links resolve into `files/harness/plugins/`, remain outside Kura v0.3's skill ownership, and are neither created nor pruned by the AI role.
