# The product-team plugin


The two-gate product pipeline ships as a plugin at `roles/ai/files/claude/plugins/product-team/`, not as global skills.
It bundles eleven skills (the nine numbered stages, `setup-strategy`, and `product-lead`) with the seven agents the stages dispatch (`competitive-researcher`, `user-evidence-researcher`, `market-sizer`, `strategy-checker`, `pm-red-team`, `ac-writer`, `adr-scribe`).
The pipeline is per-repo by nature: every stage writes `docs/initiatives/<slug>/` and reads `docs/strategy/`, so only a repo actually running initiatives needs it loaded.

`product-lead` lives *inside* the bundle because it owns the pipeline's shared library: `references/conventions.md` (gates, gate medium, deferrals, profiles), twelve templates, and `scripts/pt.py`, which every stage reaches via `../product-lead/`.
A thin signpost skill of the same name stays at `skills/product-lead/` and carries the bundle's only registry row: it holds no mechanics, it just names the install command and the namespaced entry point so the pipeline stays discoverable in a repo that has not installed it.

Two loading facts matter, and both are easy to miss:

- **Artifacts are namespaced by plugin name.** A bundled skill loads as `product-team:<skill>` and a bundled agent as `product-team:<agent>`, so the commands are `/product-team:2-write-prd`, not `/2-write-prd`. Stage bodies, the README table, and the templates all use the namespaced form. The `name:` field in each file's frontmatter stays **bare**: Claude Code applies the prefix, it is never written into the artifact.
- **A project plugin only loads in a trusted workspace, after a relaunch.** Accept the trust dialog or run `claude-kit trust --on`, then restart Claude from the repo root. `claude-kit add` checks the workspace and says whether it is trusted on every plugin install, and `claude-kit doctor` reports a project with plugins linked into an untrusted workspace. See [workspace trust](../../roles/ai/files/scripts/claude-kit/ARCHITECTURE.md#workspace-trust) for why the flag alone is not the whole answer.

**Stage 4 writes two artifacts, and the UX spec comes first.** `04-ux-spec.md` (flows, every surface, every state each one can reach, and the design-system pieces that do not exist yet) is written by `ux-shaper` before `04-design-doc.md`, because states drive the data contract: a paginated empty state changes the API sketch and an optimistic interaction changes the mutation contract. Designing first and discovering the states later is how a contract ships that one of them cannot render. It runs on every initiative, including one with no UI, where it argues the absence per R# in a `## No user-facing surface` section: the pipeline's rule is that absence is argued, never asserted, and `dor-checklist.md` has always failed a bare "N/A".

That spec closes a loop that was open. `templates/story.md` has always carried a `## Design / UX note`, `dor-checklist.md` blocked a story on it and `ac-writer` read it, but **no stage wrote it**, so a field consumed by a gate and an agent was produced by nobody, and `design-doc.md` has no UX section at all. Stage 5 now points each story's note at the flow anchor it implements, and `pt.py check` follows the pointer instead of accepting prose.

**Two gates, not four.** Gate 0 (worth building) and Gate 1 (the right requirements) survive; the design and Definition of Ready gates do not. The genuinely-open design decisions at stage 4 resolve without a human in the loop, and the ones that do not are reached at implementation whether or not a gate sat there, so a PR gate over `04-design-doc.md` was buying a day of wall clock. The DoR gate produced, across three initiatives, one repeated lexical defect (an `L`-sized story whose split rationale lived in the epic because the story template had no row for it) and burned two gate PRs on it. Gate 1 now sits **after** `3-red-team` rather than before: requirements worth approving are the ones that survived an attack, and on `multi-device` the gate was answered first and the report then had to amend an already-approved PRD. The per-medium protocol (session's one `AskUserQuestion`, pr's branch-per-gate machinery) lives in `references/gates.md` and is loaded only by the gated stages, so the seven ungated ones stop paying ~380 tokens per run for a protocol they never follow.

**A gate answered in session must record its reason.** `gate_medium: session` is the default and costs seconds against a PR gate's day, but a PR leaves the reviewer's thinking in its comments and an `AskUserQuestion` leaves nothing, so the STATUS.md gate row carries decider, date **and** one line on what convinced them. Without it, `approved` is indistinguishable from nobody having read the artifact, which is a worse position than the gate cost bought.

**Stage order is derived, and `STATUS.md` holds only decisions.** [scripts/pt.py](../../roles/ai/files/claude/plugins/product-team/skills/product-lead/scripts/pt.py) reports each stage as `done`, `partial`, `ready` or `blocked` from the artifacts on disk, so the eight-row state machine every stage used to read and rewrite twice per run is gone; what a file listing cannot derive (who decided a gate, why, what killed the initiative) is what stays in the file. The script owns two more jobs, and the split is by who can decide: `check` does the lexical DoR items including the **coverage set difference** that nothing used to check, split into errors (broken references, wrong at any point) and warnings (incompleteness that is normal mid-pipeline), and `spec-merge` applies shipped requirements to `docs/specs/`. `6-verify` runs `check --strict` first, where warnings fail too, and judges only testability, slice verticality, spine completeness and unowned questions, pinned to `model: sonnet`; in `solo`, `check --strict` from the decompose handoff **is** the Definition of Ready.

`partial` exists because of the repo's own history: two initiatives on disk completed stage 4 before `04-ux-spec.md` was an artifact at all, and a stage judged only complete-or-not reported them `ready`, telling the reader to re-run a stage that had finished, below two stages already reading done. The same rule covers a legacy `05-backlog/` with no `05-tasks.md`. Both were caught by running `pt.py status` against the three real initiatives before the stage table was deleted, which is why that comparison is the one verification step that had to happen first.

**Requirements carry their scenarios, and the ids are the currency.** `02-prd.md` holds `### R3: {name}`, a SHALL sentence, a `Capability:` line and `#### R3.S1` WHEN/THEN blocks. Four consumers read those ids: a story claims them instead of restating them (which is what took the backlog from 1,489 lines to roughly 420), a task cites them, `pt.py check` counts them, and `spec-merge` copies them. The old shape put the requirement in stage 2 and its criteria in stage 5, written by a different agent into a different file, and what went unwritten was every constraint nobody thought to phrase as a feature: a real initiative shipped a note field whose "unbounded" was agreed in conversation and stated in no artifact. `ac-writer` therefore **claims and completes** rather than authors, and a slice needing a criterion the PRD lacks is a reported PRD gap.

**`05-tasks.md` exists because a story could never describe the spine.** A story must trace to a requirement and no requirement asks for a toolchain, so setting the project up, deploying it, and accepting it where it runs were rediscovered at implementation time, and all fifteen stories on the first initiative carried none of the three. Tasks lift the requirement-trace rule (a task may name a scenario, a design decision, or `infrastructure`), and their `- [ ]` checkboxes are what `spec-merge` reads to decide what shipped.

**A deferral is a forward handshake, and the checker is what makes it one.** An artifact may hand a question to one that runs after it, the resolver must close it by name, and `pt.py check` fails an unclosed one, a backwards one, or one naming a non-artifact. Without that check a deferral is a comment. The value is not bookkeeping: an artifact allowed to say "not mine, the design decides" stops hedging, which is what lets the upstream ones get shorter. `05-tasks.md` has no such section, deliberately, because nothing runs after it; a deferral aimed *at* it is closed by a task line citing the id.

**The config is a file, not a CLAUDE.md section.** `docs/strategy/product-team.yml` holds the `profile`, the `gate_medium`, the gate owners and the `roster`, and the repo's CLAUDE.md section is three lines pointing at it: the old 23-line block was loaded on every turn of every session in that repo for the benefit of eight skills that can open a file when they run. `pt.py` reads only the top-level scalars, so there is no partial YAML parser to get wrong; the nested `roster` and `gate_owners` are read by the stage skills, which have a real one. The `roster` is how a repo stops paying for a pass that cannot tell it anything, and `ux_spec` deliberately has no `none` value.

**`profile: solo` drops the board-facing half and no findings.** No stories, no `6-verify`, no `7-push-to-board`, no PR machinery, which is roughly half the measured cost and nearly all of the latency. Research and red-team stay, because together they are 13% of the cost and produced the decision-changing findings on every initiative that ran; the old expedited path skipped exactly those two and is **deleted** rather than kept alongside. There is no shorter path, and a skip is a human decision recorded in STATUS.md.

**Only `8-living-spec` outlives the initiative.** It merges each requirement whose tasks are all checked into `docs/specs/<capability>/spec.md` at requirement level, preserving what other initiatives put there, so the repo carries what the system does now rather than a folder of proposals going stale. The specs have a lifecycle beyond append: a PRD block may carry `Modifies:` (replace, which is also rename) or `Removes:` (with mandatory `Reason:` and `Migration:`, shipped only through a task citing its bare R#) against a spec requirement's name, and a plain upsert that would silently drop a scenario the spec already holds is refused by name, because that scenario may be another initiative's. The `docs/LEARNINGS.md` retrospective moved here from stage 7 for two reasons: written at board-export time it precedes any shipping, and `solo` never runs stage 7 so a solo initiative used to get no retrospective at all. Its real risk is attendance rather than correctness, since nothing in the pipeline is present at ship, so `pt.py status` reports how many shipped requirements are still unmerged.

**`ux-shaper` is a registry agent, not bundled here, and that is the deliberate cost.** The architect needs the same artifact for work that never enters the pipeline, and one definition beats two that drift. Neither key can express the dependency: `plugin.json`'s `dependencies` is reserved by Claude Code and an agent's `dependencies` name skills, so nothing declares an agent. Stage 4 therefore checks and names `claude-kit add ux-shaper --type agent --global` rather than skipping silently, and the `global` tag means `sync` links it into `~/.claude/agents/` so the check is a guard rather than a likely path. **The architect does not spawn it**: `disallowedTools: Agent` is load-bearing there, so a UI brief with no spec in the repo returns `needs-decision` naming the run, and orchestration stays with the caller.

**Review that is not a gate is a CODEOWNERS line.** `setup-strategy` scaffolds `.github/CODEOWNERS`, so `/docs/initiatives/*/04-ux-spec.md` and `/docs/adr/` are lines there and GitHub enforces the approvals; `STATUS.md` has one `Decided by` cell per gate and adding a second decider would ripple into every stage. Order matters: CODEOWNERS applies the **last** matching pattern, so a specific line must follow `/docs/initiatives/`. Omitting the UX line is how a repo with no designer opts out.

The `docs/adr/` line is not tidiness, it is the load-bearing half of removing the design gate. Stage 4's PR gate was the only approval an ADR got, and an ADR is the one artifact class here treated as immutable and hard to reverse, so the approval moved onto the commit the human makes anyway rather than disappearing. [test_product_team.py](../../lib/python/tests/test_product_team.py) asserts `setup-strategy` still writes it, along with the three other mitigations that removing a gate depended on: each of the four is a thing that fails by silently not happening, which is exactly the class a test has to hold.

**A story carries a derived `Needs design seat` flag and still no owning seat.** The flag is copied from whether the story's flow draws on the spec's new-system-pieces section, never judged, and stage 7 turns it into a `needs:design` label so design load is countable on the board before implementation starts. Seat routing stays `architect.md`'s single responsibility: a second opinion here would be a second thing to keep in sync, which is exactly how architect's own seat list rotted from twelve seats to seven while `design`, `mobile`, `desktop`, `dx` and `gtm` shipped. `test_catalog.py` now asserts every implementer seat (a seat agent with no `tools:` allowlist, since a read-only advisor owns no slice) is named in that file, so the next seat fails CI instead of going quietly unroutable.

**A plugin bundles only what it owns.** A skill vendored from an upstream repo stays under `skills/`, because `claude-kit update --type skill` syncs it by `upstream_path` and a copy inside a plugin would silently fork from upstream.
Those are declared in `plugin.json` under **`skillDependencies`** instead, and `claude-kit add <plugin> --type plugin` installs each one's transitive closure into `<project>/.claude/skills/` next to the plugin symlink, exactly as an agent's `dependencies` are resolved.
The key name is load-bearing: `dependencies` is reserved by Claude Code, and an array of skill names there makes the plugin ship **nothing**, silently. Every agent and skill stops registering while `claude plugin details` still lists them all, so the manifest looks healthy (verified on 2.1.220). Unknown keys like `groups` and `skillDependencies` are ignored safely; `dependencies` is not.
`product-team` uses this for `idea-refine`, which is vendored from `addyosmani/agent-skills` and seeds the `setup-strategy` and `0-refine-idea` interviews.
Because the dependency is a normal skill rather than a plugin artifact, it keeps its bare name: the command is `/idea-refine`, not `/product-team:idea-refine`.
