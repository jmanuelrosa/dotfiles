# The code review policy


The review bar lives at [roles/ai/files/claude/rules/code-review.md](../../roles/ai/files/claude/rules/code-review.md), linked into `~/.claude/rules/`, and **not** in a `REVIEW.md`.
That is not a preference: `REVIEW.md` is read at a **repository root only**, by Anthropic's hosted GitHub Code Review and by nothing else.
The local `/code-review` does not read it, stated in the docs and confirmed against the binary, where scanning all 256 MB of 2.1.220 finds the string `review.md` **zero** times, so there is no dynamic path construction either.
A `~/.claude/REVIEW.md` would be a file nothing ever opens, which is indistinguishable from a policy that works.
The hosted service is also out of reach here: it is a Team/Enterprise research preview requiring Owner or Primary Owner, and this account's `organizationRole` is `user`.

What the local review *does* read is the whole `CLAUDE.md` hierarchy plus `~/.claude/rules/`, since `/code-review` runs as a **fork** inheriting the parent conversation.
Its built-in prompt already names the hook: a finding should state "which CLAUDE.md rule is broken", so conventions are a first-class category and a rules file plugs straight into it.
The policy is therefore **always-on rather than review-only**, and that is the point: it is equally the bar for *writing* a diff, so `paths:` frontmatter is deliberately absent (a path-scoped rule loads only when a matching file is read, which is not the same thing as during a review).

Rules are linked **file by file, globbed on `*.md`**, mirroring the hooks task rather than linking the directory: the documented symlink support covers links placed *inside* `.claude/rules/`, so replacing `~/.claude/rules` wholesale is the undocumented shape. `claude-kit sync` cannot prune any of it, since its stale scan reads only the `skills` and `agents` leaves and never `~/.claude` top level.

Three things the policy does that a checklist would not, and they are the parts not to weaken:

- **One severity vocabulary** (`blocker` · `important` · `nit` · `pre-existing`) replacing the four our own artifacts spoke: `code-review-and-quality` graded Critical/Required/Nit/Optional-Consider/FYI, `cc-review` P0-P2, `coderabbit` nitpick/warning, the hosted pipeline Important/Nit/Pre-existing. A reader holding four scales ranks nothing.
- **A verification bar**: a `file:line` read in the source, a concrete failure scenario, and the mechanism in one clause. Not invented here, `ReportFindings` requires `failure_scenario`. A finding that cannot state one is an opinion and is dropped rather than hedged.
- **Skip rules that refuse to duplicate a hook.** Em dashes are blocked at Write time by `em-dash-gate.sh`, lint and typecheck run at commit time via `pre-commit-verify.sh`, and `--no-verify` is blocked by `git-skill-gate.sh`. Reporting any of them spends the output cap teaching the reader that the report is padding.

The **eight axes are ranked**, because the built-in review cuts from the bottom when the cap bites: correctness, contract and rollback, security, failure visibility, test adequacy, performance, convention, simplification.
Three of them are covered by no skill here at all (contract and rollback, failure visibility, test adequacy), which is most of what the policy adds beyond routing.
Axes route to a seat's **`<seat>:<seat>-failure-modes` skill**, never to a reference filename, so retitling a reference upstream cannot strand the policy; the seat's own trigger table picks the references. Seats are plugins, so the policy checks for one and says the deep checklist was unavailable rather than assuming presence.

**The reviewer never mutates**, and the ban is by name: `/code-review --fix`, `code-simplification`, `/simplify`, `knip --fix`, `coderabbit`, `pr`, `performance-optimization` from step 3, and `cc-review`'s apply step all write. `--fix` is named first because it is the one the harness itself ships, and a list of only other people's writers reads as complete while leaving unmentioned the flag a reviewer is likeliest to reach for. `cc-staff-reviewer` reviews the Claude Code setup and never application code, so no code finding routes there.

**Effort is pinned at every call site, and the policy's table is the authority.** The level is `/code-review`'s first argument and it decides the shape of the run, not just the bar: one diff pass with no verify step at `low`, eight finder angles with a one-vote verify at `medium`, a recall-oriented net from `high` up. Since the command carries `disableModelInvocation: true`, nothing can pass it on a caller's behalf, so every one of the twenty references in `files/claude/` is prose telling a human what to type and a bare one silently asks for the default however large the diff is. A seat's completion report pins `high` (one slice, a stack the reviewer has not seen), `feature-team` and the story loop in the two READMEs pin `max` (a multi-seat, multi-worktree integration). `test_review_policy.py` scans the seat agents, `feature-team`, `GETTING-STARTED.md` and `README.md` and fails on any occurrence not followed by a level, and separately asserts every level in the vocabulary appears in the table, so a level cannot be pinned without being documented. Upstream skill trees are out of that scan for the same reason the policy's own skip rules exclude them.

**`code-review-and-quality` is superseded as a reviewer, and the retag is the only lever available.** Its five axes are a subset of the eight (it has nothing on contract and rollback, failure visibility, or test adequacy) and its Critical/Required/Nit/Optional-Consider/FYI scale is one of the four dialects the policy exists to collapse, so the policy states that the axes and severities there win and that what the skill is still good for is review *technique*: change sizing, describing a change, handling disagreement, dependency discipline. Its body cannot be fixed, because it is upstream from `addyosmani/agent-skills` and `claude-kit update --type skill` replaces the tree wholesale. What can be fixed is its `groups`: dropping `review` (keeping `refactoring`, `backend`, `frontend`) is what stops `scout` and `--group review` offering a rival reviewer to every JS project. That survives a sync only because `registry.stamp_entry` writes `updated_at` and leaves every other key byte-identical, which is an assumption load-bearing enough that a test asserts the tag has not come back. `code-simplification` and `performance-optimization` keep all four tags and are not superseded at all: axes 6 and 8 report a mechanism and defer the fix to them, so they are the separate mutating pass the ban above assumes exists.

**There is no `REVIEW.md` here, and no template for one.** A `templates/REVIEW.md` shipped as the dormant half of this policy and was deleted, because both of its consumers are out of reach: hosted Code Review needs the Owner role this account does not have, and the `claude-code-action` workflow that could read it is a workflow nothing in this repo ships. A dormant artifact no run reaches and no test can exercise is indistinguishable from one that works, which is the same failure mode the policy avoided by not being a `REVIEW.md` in the first place. Write one at the repository root that reads it on the day hosted Code Review is enabled, condensed from the policy and self-contained, since it is pasted verbatim and `@` imports are silently not expanded.

**The policy does reach pi, through `REVIEW_GUIDELINES.md`, and that is not the decision above reversed.** The paragraph above is about `REVIEW.md`, the filename hosted Code Review reads, and it still holds: that consumer needs an Owner role this account does not have. `pi-review`, which ships in `files/pi/settings.json` `packages`, is a different consumer reading a different filename, and it is installed. It appends a `REVIEW_GUIDELINES.md` to its review prompt and its own rubric defers to project guidelines explicitly, so the four severities and the eight ranked axes arrive intact.

Two mechanics decide the shape. The file is a **relative symlink** to `rules/code-review.md`, because a condensed copy is the drift this repo links its configs to avoid, and the cost is that a few Claude-only sentences (the `/code-review` effort levels) ride along where pi has no counterpart. And `pi-review` reads it **only from a directory that also holds a `.pi` directory**, then stops walking, so `.pi/` exists at the repository root for no other purpose. Nothing else belongs in it: an entry pi counts as project config (`settings.json`, `extensions`, `skills`, `prompts`, `themes`, `SYSTEM.md`, `APPEND_SYSTEM.md`) would make pi ask to trust this checkout on every session, and a test asserts none appears.

This is deliberately **not** automated for every project. `claude-kit` creates no root-level files anywhere, so a repo that wants pi reviews on this bar adds the two entries by hand, which is one symlink and one directory.

[test_review_policy.py](../../lib/python/tests/test_review_policy.py) holds what remains: the policy is linked and its parent directory created, no `REVIEW.md` reaches `~/.claude` by either route, the pi guidelines link resolves to the policy and `.pi/` stays free of project config, every seat the policy routes to actually ships, and every banned mutator still exists under the name the ban uses.
