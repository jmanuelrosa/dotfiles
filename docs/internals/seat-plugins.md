# Seat plugins & the staff-engineer fleet


Staff-engineer seats are one of two plugin classes here (the other is [product-team](product-team.md)), and plugins are the artifact class that lives outside the registries. A seat is a self-contained plugin at `roles/ai/files/claude/plugins/<discipline>/` bundling the agent with its paired failure-modes skill: `.claude-plugin/plugin.json`, `agents/<discipline>-staff-engineer.md`, and `skills/<discipline>-failure-modes/SKILL.md` alongside a `references/` directory of 8-10 checklists. Fifteen ship today: analytics, backend, cloud, data, database, design, desktop, dx, frontend, gtm, mobile, platform, qa, security, sre. **These carry no `agent-registry.json` or `skill-registry.json` rows**: `plugin.json` is their metadata, holding `name`, `description`, `version`, `author`, and a `groups` array drawn from the same controlled vocabulary as the registries, and the catalog discovers a seat by finding that manifest under `plugins/` rather than by reading a list. `claude-kit add <discipline> --type plugin` symlinks `plugins/<discipline>` into `<project>/.claude/skills/<discipline>`, where it loads as `<discipline>@skills-dir`.

**A seat's frontmatter pins `model`, `effort` and `memory`, and all three are identity rather than preference.** `model: opus` is a deliberate refusal to follow a `/model fable` session, so the cost of a delegated implementation stays predictable whatever the caller is running. `effort` is the dial the session default cannot set correctly for a delegated agent: the caller picks their level for their own turn, so an implementer seat carries `xhigh` for multi-file work against an unfamiliar stack and the `security` advisor carries `high`, since it reads far more than it writes and Opus 5 review accuracy does not need the extra depth. `high` matches the current `effortLevel` and so looks inert, but it is a pin: it is what keeps the advisor off an `xhigh`, `max`, or ultracode session that the caller chose for their own turn. `memory: project` gives each seat `<project>/.claude/agent-memory/<name>/`, which is what closes the loop the completion report's "Discovered gotchas" section used to leave open by hand: the seat keeps the stack facts it discovered, and the report still names them for the caller. That directory is committable by design, so a seat records the shape of the codebase there and never a secret or a security finding's exploit detail. The `## Boundaries` ✅ Always list carries the bullet that makes the seat actually write there; an advisor seat has no `Boundaries`, so its bullet is the last of the `## Hard rules`.

**Fourteen of the fifteen are implementer seats, and `architect.md` must name every one of them:** twelve by name in its specialist list, plus `frontend` and `backend` as the fallback pair it defaults to when no specialist is installed. A seat it names nowhere is a seat it never assigns a slice to, and it falls back to frontend or backend instead, which is indistinguishable from routing correctly. That is not hypothetical: the specialist list stood at seven for as long as `design`, `mobile`, `desktop`, `dx` and `gtm` had been shipping. `security` is the one seat correctly absent, because an advisor is read-only and owns no slice, and its `tools:` allowlist is what makes the split machine-readable: `test_catalog.py` pins the advisor set and asserts every other seat agent appears in that file.

**`design` versus `frontend` is the subtle boundary, and it is a layer split rather than a taste one.** The `design` seat owns the system (tokens, theming, shared components and their variant APIs, motion primitives, palette-level contrast); `frontend`, `mobile` and `desktop` own feature UI that composes it. So the architect creates a design slice **only** when the work touches that system layer, orders it before its consumers, and writes the shared token or prop names into `## Contracts` like any other cross-slice contract. Feature UI composing what already exists needs no design slice, and an empty one to keep the seat involved is worse than none: it collides with the no-two-slices-own-the-same-file rule. The three consuming seats carry an ask-first bullet for inventing a token or shared component, so they stop before shipping a one-off rather than naming it in the report afterwards; the line there is systemic versus local, and a genuinely single-use layout value stays theirs. `ux-shaper` (a registry agent, see [product-team](product-team.md)) specifies flows, surfaces and states; it deliberately produces no visual direction, which is the design seat's own.

**The design seat owns the look, not only the system, and there is no design-to-frontend handoff.** It was for a while a pure conformance engine: 52 pass/fail rules across ways of thinking, red flags, ask-first gates, never rules, the self-check and the rationalization table, and not one of them asking whether the result was any good. That agent passes its own gate on the median and always will, because correctness is a floor and a floor makes no choices. Three things close it, and the first is the load-bearing one:

- **Step 2, "Commit the direction", runs on every brief and cannot be deferred.** It states the subject's world, a thesis for the first viewport, and one signature element, then takes a defended position on nine axes (scale range, type pairing, palette and strategy tier, material, bleed, grid, subject artifact, density, motion). **"The framework default", "the system default" and "none" are failing answers.** It sits after stack detection rather than before, because detection is what reveals whether a system already exists. At surface altitude it writes `docs/design/direction.md`, tracked in git for the same reason `docs/plans/` and `docs/adr/` are: the next brief composes the same design instead of re-inventing it. The consuming seats read that file in their own Step 1 and carry an ask-first bullet against contradicting a recorded axis.
- **The ask-first gates are conditioned rather than absolute.** They exist to protect decisions someone already made, so with no design system and no recorded direction the scale, palette and typeface gates guard nothing and inventing them *is* the brief; recording the choice arms them for next time. The dependency and breaking-change gates never relax, because they cost the project something either way. Without this, dropping an origination skill into a seat whose boundaries forbid picking a typeface just produces `needs-decision`.
- **`references/craft-and-distinctiveness.md`** is the tenth failure-mode reference and the only one asking whether the design is good rather than correct. Its refusals are extracted from the craft floor of [pbakaus/impeccable](https://github.com/pbakaus/impeccable) (Apache-2.0): the eyebrow above a heading, the grid of identical cards, gradient text, monospace as a costume, and the three looks machine-generated design converges on regardless of subject. impeccable itself is deliberately **not** tracked here: it is 148 files and 72,000 lines of bundled Node with its own subagents, decision server and OpenAI-billed comp round, and its four review agents live outside the skill path anyway, so a registry entry for it would import a competing orchestrator arriving permanently degraded. The doctrine is ~3% of it and the only portable part.

`frontend-design` and `emil-design-eng` arrive through the design plugin's **`skillDependencies`** and are routed by a trigger table rather than a flat inventory sweep, since emil alone is ~7,300 tokens and roughly 60% motion, which is more than all nine other references combined for one domain's coverage. `frontend-design` was **removed from the frontend seat's routing list**: origination behind a gate and origination beside it are not the same offer, and leaving both doors open widens the gap the gate was added to close.

Two seat variants exist and the difference is deliberate, not drift. The **implementer seat** carries a fixed 13-section skeleton: an operating loop, three numbered steps (detect the stack, route to installed skills, open the failure-mode checklists), then ways of thinking, red flags, boundaries, a verification gate, a pre-handoff self-check, common rationalizations, and a structured completion report. The **advisor seat** (`security` today) is read-only, declares a `tools:` allowlist, and swaps three sections: hard rules up front, escalation triggers in place of the verification gate, and an output contract in place of the completion report. [references/advisor-adaptation.md](../../roles/ai/files/claude/skills/agent-writer/references/advisor-adaptation.md) defines that divergence.

The failure-modes `SKILL.md` is a router, not content. Its body is an intro asserting that an unresolved item blocks `done` and escalates as `needs-decision`, a two-column trigger table mapping "the brief or diff touches …" to a `references/*.md` file, and a coda declaring the shape every reference follows: **Failure modes to rule out** (each bullet carrying a `Check:`), **Escalation triggers**, and **What good looks like**. References are stack-agnostic by design, so a seat is useful before the project's framework is known. Two reference names are shared vocabulary and should not be re-coined per seat: `failure-visibility.md` covers whether a failure surfaces with correlating identity (11 seats), and `errors-and-resilience.md` covers UI error boundaries, fallback states, and retry semantics (`design`, `desktop`, `frontend`). `sre` is exempt from both because it is the observability seat itself, splitting the concern across nine specialized references.

Authoring or upgrading a seat goes through the [agent-writer](../../roles/ai/files/claude/skills/agent-writer/SKILL.md) skill, which owns the whole pipeline: mode selection, the two-researcher protocol, seat anatomy, the failure-modes template, coherence rules, packaging, the fresh-eyes audit, and the verification sweep. `backend` and `platform` are the canon exemplars, and the skill is explicit that they get read in full rather than the pattern being re-derived from memory.
