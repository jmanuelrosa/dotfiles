# Acceptance criteria live on the branch, then in one comment


The [ac](../../roles/ai/files/claude/skills/ac/SKILL.md) skill keeps a Jira-tracked branch's acceptance criteria in `<toplevel>/.claude/state/ac/<KEY>.md` while the work happens, and `/ac push` publishes them to the ticket as a single comment. The point of the local copy is ordering: criteria written from a finished diff always pass, so they measure nothing, and a file that exists before the first commit is the only cheap way to get them written first.

**AC are authored in four places in this repo and only one of them is this skill.** The `product-team` plugin's `ac-writer` owns PRD-traced story ACs, `planning-and-task-breakdown` owns per-task ACs, and `architect` owns spec-level criteria. None of the three overlaps here: `ac-writer` in particular cannot be reused, since it has no Bash and so can never reach acli, its contract is traceability to `R#` ids indexed from `02-prd.md`, and it reports and does nothing when those ids are absent, which is every bare Jira ticket. The one thing this skill does share is the grammar, which lives in `adf.py`.

Four things carry the design:

- **`adf.py --comment` is the whole mechanism, and there is no second script.** It relaxes `REQUIRED` to acceptance-criteria-only, renders that section alone under its green lozenge, and appends the footer warning that edits in Jira are overwritten. That is what makes the local file a *pure* `adf.py` template with no metadata header and no extra sections: it is handed to the script verbatim, so nothing between the file and the ticket can garble it. It also means the file is a valid ticket description body the moment someone adds a `## Context`.
- **The comment id is a sidecar, not a marker in the body.** `<KEY>.comment-id` holds the comment id on line 1 and the sha256 of the published body on line 2: the first decides create versus update, the second makes a re-push with nothing changed a no-op that calls acli not at all. Identity from body text was designed and rejected: `acli jira workitem comment list` returns bodies flattened to plain strings with text nested in lists dropped entirely, and a marker a human can see is a marker a human can delete, at which point every push appends another comment forever with no error anywhere. The hash is over the generated ADF rather than the markdown, because that is what actually reaches the ticket, and because an `update` rewriting a byte-identical body still moves the issue's `updated` timestamp and so perturbs every `ORDER BY updated` board and the `weekly-recap` query.
- **`create` and `update` disagree about ADF.** `comment create` reads it through `-F/--body-file`; `comment update` ignores ADF on that flag and needs `--body-adf`. Getting it backwards posts a raw JSON document to the ticket, which is why the skill states the two forms as a table rather than as prose.
- **The scope gate is two conditions, and the second is the load-bearing one.** The branch must be `<type>/<KEY>-<slug>`, and `KEY`'s prefix must equal `$JIRA_PROJECT`. Only the work profile exports that variable, so the skill is inert on a personal machine; and the prefix check is what stops `context.py`'s key shape from firing on `fix/UTF-8-decoding-bug`, `HTTP-2` or `ISO-8601`, all of which parse as Jira keys and would otherwise mean an acli call against a real Jira instance.

The working copy is **never committed, and a per-repo `.gitignore` line is the mechanism**, not a machine-wide refusal like the one guarding `.claude/tasks/`. The skill appends `.claude/state/ac/` when `git check-ignore` says the repo lacks it. Two reasons it goes here rather than into the `commit` and gate guards: the rule is tracked, so a `wt` worktree inherits it for free, and it covers every tool rather than only the two paths those guards see, including a bare `git add -A` and anything an editor does. The entry stops at `state/ac/` rather than `state/` because `.claude/state/` also holds research memos, which `research/SPEC.md` deliberately leaves the user free to track, and a `.claude/state` line would silently ignore those too (verified with `git check-ignore`).

The tradeoff is real and was taken deliberately: an ignored path can still be forced in, and git's own refusal prints `hint: Use -f if you really want to add them`, which is an instruction an agent reading the error may follow. A `.gitignore` line is a barrier against carelessness rather than against determination, and it is the right altitude for a file whose worst case is noise in a diff.

`/pr` is untouched, and publishing is deliberately not wired into it. Two reasons, both verified: acli is only exempt from the sandbox as a **leading token**, so it cannot be spawned from inside `apply.py` at all, and `apply.py` is not idempotent, so a publish-only retry would re-push and re-run `gh pr create`. Publishing is therefore its own explicit act.
