# XML processing and deserialization

When to read: the brief, diff, or assessed surface touches parsing or validating XML (SOAP, SAML or other XML payloads, XSLT transforms, XSD/DTD validation, XPath over parsed documents), XML parser or schema factory configuration, or deserializing data through native object serialization (Java `Serializable`, .NET `BinaryFormatter`, Python `pickle`, PHP `unserialize`), YAML object loaders, or JSON/XML libraries that resolve types from the payload.
Sources (OWASP Cheat Sheet Series, CC BY-SA 4.0): [XML External Entity Prevention](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html), [XML Security](https://cheatsheetseries.owasp.org/cheatsheets/XML_Security_Cheat_Sheet.html), [Deserialization](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html)

## Deserializing untrusted data

- **Untrusted data passed to a native object deserializer.** Native serialization formats can be repurposed for denial of service, access control bypass, or remote code execution; avoid them for untrusted data and switch to a pure data format (JSON, XML) with data-transfer objects, remembering that the application can still make mistakes after a pure data object is parsed.
  Check: search for `unserialize()`, `pickle.load`/`loads`, `jsonpickle.decode`, `ObjectInputStream.readObject`/`readUnshared`, `readResolve`/`readExternal`/`readObjectNoData` overrides, `XMLDecoder`, XStream `fromXML`, and `BinaryFormatter`, and confirm none receive data an external party can influence; move the boundary to a data format. Owner: `backend`. Source: Deserialization.
- **Payload chooses the type the deserializer instantiates.** Do not let the data stream define the type of object it is deserialized to; prefer serializers bound to a declared type (for example `DataContractSerializer` or `XmlSerializer` in .NET), and prevent attackers from steering the type by any route, including a type name read from a database the attacker can write.
  Check: no type-name field, `@type`, `$type`, or `Type.GetType(<data>)` drives instantiation; deserialization targets a type fixed in code. Owner: `backend`. Source: Deserialization.
- **Type check performed after deserialization.** Code can execute inside certain types during deserialization, so inspecting the object's type afterwards is too late; restrict types before instantiation, for example with a custom `SerializationBinder` for JSON.Net.
  Check: any type allowlist is enforced by a binder, resolver, or filter consulted during deserialization, not by an `is`/`instanceof` check on the result. Owner: `backend`. Source: Deserialization.
- **Type allowlist that admits dangerous types.** When self-describing streams are unavoidable, restrict the allowed types, knowing this stays risky: many platform types are dangerous themselves (a deserialized `FileInfo` can change real file properties) and allowed types with `Object`-typed properties (such as `ValidationException.Value`) let an attacker smuggle any type. Track known gadget types and watch where your deserializers can create them.
  Check: every allowlisted type is a simple data type with no polymorphic `Object` members and is not a known gadget (for example `AssemblyInstaller`, `WorkflowDesigner`, `ResourceDictionary`, `ObjectDataProvider`, `BindingSource`, `ExchangeSettingsProvider`, `DataViewManager`, `XmlDocument`/`XmlDataDocument`, `PSObject`). Owner: `backend`. Source: Deserialization.
- **Gadget-bearing code linked into an internet-facing deserializing service.** A deserializer can only instantiate types it knows about, so keep code that could provide gadgets separate from code with internet connectivity (for example, no WPF assembly carrying `ObjectDataProvider` referenced by a REST service that deserializes untrusted data).
  Check: project references of services that deserialize external input exclude UI and automation assemblies that host known gadgets. Owner: `backend`. Source: Deserialization.
- **Serialized messages accepted without an authenticated signature.** When the application knows in advance which messages it will process, sign them during serialization and refuse to deserialize any message without a valid signature.
  Check: the deserialization entry point verifies a signature or MAC before decoding, and failure aborts. Owner: `backend`. Source: Deserialization.
- **Java deserialization without a serialization filter.** Configure Java serialization filters with an application-specific class allowlist and resource limits (graph depth, references, array lengths, stream bytes) before reading objects, and bound the serialized input size separately because filters are not called for concretely encoded strings or primitives. A `resolveClass()` allowlist does not see strings or proxy classes (resolved through `resolveProxyClass()`) and does not bound resources; no filter makes arbitrary untrusted deserialization safe.
  Check: every `ObjectInputStream` reading external data has an `ObjectInputFilter` (or JVM-wide filter) with an allowlist and limits, plus an input size cap. Owner: `backend`. Source: Deserialization.
- **Domain objects deserializable only because of their class hierarchy.** When objects must implement `Serializable` through inheritance but must never be deserialized, declare a `private final readObject()` that always throws.
  Check: serializable domain classes not meant for deserialization define a throwing `readObject`. Owner: `backend`. Source: Deserialization.
- **Sensitive or trusted fields included in serialization.** Fields that end users must never control during deserialization or see after serialization are declared `private transient`.
  Check: secrets, computed financial fields, and authorization state on `Serializable` classes are `transient`. Owner: `backend`. Source: Deserialization.
- **Third-party Java code deserializing without a patch path.** If you do not own the code or cannot wait for a patch, weave hardening into `ObjectInputStream` with a Java agent (`-javaagent:`); a global change is only safe as a denylist of known gadget types because expected classes differ per application.
  Check: JVMs running unpatchable deserializing components start with a hardening agent in their launch flags. Owner: `platform`. Source: Deserialization.
- **Serialized object formats crossing a trust boundary.** Native serialization on the wire is detectable: Java streams start with hex `AC ED 00 05` (base64 `rO0`) or use `Content-Type: application/x-java-serialized-object`, base64 pickle often starts with `gASV`, .NET `BinaryFormatter` base64 starts with `AAEAAAD/////`, and `TypeObject` or `$type:` marks .NET type metadata.
  Check: API contracts, fixtures, and handlers for inbound data contain none of these markers or content types; any that do are routed to the controls above. Owner: `backend`. Source: Deserialization.

## Deserialization library and runtime settings

- **.NET `BinaryFormatter` in use.** Microsoft states `BinaryFormatter` is dangerous and cannot be secured; it must not be used.
  Check: no `BinaryFormatter` reference remains in the diff or its dependencies' call paths. Owner: `backend`. Source: Deserialization.
- **JSON.Net or `JavaScriptSerializer` resolving types from the payload.** Set JSON.Net `TypeNameHandling` only to `None`, and never use `JavaScriptSerializer` with a `JavaScriptTypeResolver`.
  Check: search for `TypeNameHandling` and `JavaScriptTypeResolver`; any value other than `None` or any resolver use is a finding. Owner: `backend`. Source: Deserialization.
- **Python unsafe loaders on untrusted input.** Never unpickle untrusted data (`pickle.load`/`loads` can execute arbitrary code), never pass untrusted input to `jsonpickle.decode()`, and load untrusted YAML only with `yaml.safe_load()`, not `yaml.unsafe_load()` or `yaml.load()` with `Loader=yaml.Loader` or `yaml.UnsafeLoader`, without registering custom constructors that allow arbitrary object creation.
  Check: grep for these calls and loader arguments on paths that read external data. Owner: `backend`. Source: Deserialization.
- **PHP `unserialize()` on external parameters.** Review how `unserialize()` receives external parameters and use a standard interchange format such as JSON (`json_decode()`/`json_encode()`) for data passed to or from users.
  Check: no request, cookie, or stored user value reaches `unserialize()`. Owner: `backend`. Source: Deserialization.
- **Java data-binding library configured into an unsafe mode.** fastjson2 is safe only with `autotype` off; jackson-databind only without polymorphic typing; Kryo 5.0.0+ only with class registration left on (Kryo before 5.0.0 and wrappers such as Chill must turn registration on); YamlBeans 1.16+ only without `UnsafeYamlConfig`; XStream 1.4.17+ only with its allowlist and security controls unrelaxed; fastjson 1.2.68+ only with `safemode` on; json-io only in non-typed mode (`JsonReader.USE_MAPS`) or with a custom deserializer controlling classes, since its `@type` property allows any class; SnakeYAML only with `SafeConstructor`.
  Check: library configuration in the diff matches these settings for any instance that reads external data. Owner: `backend`. Source: Deserialization.
- **Java deserialization library at an unsafe or abandoned version.** Do not use Castor (abandoned), fastjson before 1.2.68, the JDK `XMLDecoder`, XStream before 1.4.17, or YamlBeans before 1.16 with untrusted input, since these allow deserialization of any class or cannot be secured.
  Check: dependency manifests and lockfiles pin none of these for components that read external data. Owner: `dx`. Source: Deserialization, XXE Prevention.

## XML external entities and DTDs

- **DTDs accepted in untrusted XML.** Disable document type definitions whenever possible and reject DOCTYPE declarations if the parser supports it; if DTDs are required, disable external entity resolution and external DTD loading and limit entity expansion. SOAP forbids DTDs, so a SOAP processor should reject any message containing one.
  Check: every parser that reads external XML is configured to reject DOCTYPE, or to disable external entities and external DTD loading with expansion limits when DTDs are justified. Owner: `backend`. Source: XXE Prevention, XML Security.
- **XInclude enabled.** XInclude loads resources independently of DTDs; keep it disabled unless explicitly required.
  Check: no parser factory enables XInclude-aware parsing for external input. Owner: `backend`. Source: XXE Prevention.
- **Processing continues after a security setting fails.** Treat an unsupported security setting as a configuration failure: stop processing rather than catching the exception and parsing untrusted XML with partial hardening. Third-party providers selected by a factory lookup may not support the same controls.
  Check: exceptions from setting parser features or properties propagate or abort; no `try/catch` around hardening calls swallows failures. Owner: `backend`. Source: XXE Prevention.
- **Untrusted filename or URL passed directly to a parsing API.** External-entity controls do not restrict access to the initial resource given to a parsing or processing API, so pass streams, not untrusted filenames or URLs.
  Check: parse calls receive a stream or byte buffer from the request, never a path or URL derived from input. Owner: `backend`. Source: XXE Prevention.
- **Custom entity resolver that falls back to default resolution.** A resolver that returns `null` for an unapproved resource usually delegates to the parser's default resolution; resolvers must actively reject unapproved identifiers (Java `EntityResolver` throwing `SAXException`, Xerces-C with default resolution disabled so a `NULL` return cannot fall back).
  Check: every custom resolver throws or returns an empty/rejecting source for identifiers outside an explicit allowlist. Owner: `backend`. Source: XXE Prevention.
- **Wrapper or convenience API that discards the hardened configuration.** Wrappers and convenience overloads can parse internally or replace the reader's resolver: Java `SAXParser.parse(source, DefaultHandler)` replaces the resolver (call `reader.parse(...)` directly), `XPath.evaluate` with an `InputSource` parses internally (evaluate against a document from the hardened builder), JAXB `unmarshal` of raw XML delegates parser setup to the provider (pass a hardened `XMLStreamReader`), dom4j needs `SAXReader.setXMLReader` plus `setEntityResolver`, JDOM needs `SAXBuilder(XMLReaderJDOMFactory)`, Commons Digester needs `setEntityResolver` before parsing, and .NET `XPathNavigator`, `XslCompiledTransform`, and `XmlDictionaryReader` are only as safe as the parser handed to them.
  Check: each wrapper or overload in the diff is fed a hardened reader or parser and its resolver is re-applied where the wrapper replaces it. Owner: `backend`. Source: XXE Prevention.

## XSLT, schemas, and external resources

- **Stylesheet or schema processing allowed to fetch external resources.** XSLT imports, includes, and `document()`, and schema compilation and validation, load resources independently of external entities, so restrict external access during transformation and validation as well as parsing. In JAXP: on `TransformerFactory` set `FEATURE_SECURE_PROCESSING` and `ACCESS_EXTERNAL_DTD` and `ACCESS_EXTERNAL_STYLESHEET` to `""` before compiling; on `SchemaFactory` set `FEATURE_SECURE_PROCESSING` and `ACCESS_EXTERNAL_DTD` and `ACCESS_EXTERNAL_SCHEMA` to `""` before `newSchema`; install any resolver on the schema factory and on every `Validator` and `ValidatorHandler`, which do not inherit it; set a `URIResolver` on the transformer factory before `newTransformer`. For other providers, supply input, schemas, and stylesheets through a `SAXSource` with a hardened namespace-aware reader and install a rejecting `URIResolver` or `LSResourceResolver`, since the input parser's settings do not cover these dependencies.
  Check: transformer and schema factories are configured before compilation, and validators carry their own resolver. Owner: `backend`. Source: XXE Prevention.
- **Stylesheet or schema chosen by the input document.** Choose the stylesheet in application code and never trust a stylesheet reference from the input document; secure-processing settings are not a sandbox for untrusted stylesheets. Use a local copy or a known good repository instead of the schema referenced in the document, and do not rely on embedded schemas, which are only a suggestion unless their integrity is checked.
  Check: stylesheets and schemas are loaded from application-owned resources, and document-supplied schema locations and inline DTDs are ignored or rejected. Owner: `backend`. Source: XXE Prevention, XML Security.
- **External dependencies allowed by protocol rather than by resource.** `ACCESS_EXTERNAL_*` properties restrict protocols, not individual resources, so allowing `https` is not an allowlist; when external dependencies are required, map approved identifiers to local resources with a catalog using `RESOLVE=strict`, or an allowlisting resolver that rejects everything else, and own the safety of what your resolver returns.
  Check: required external schemas or DTDs resolve through a strict catalog or allowlist to local copies. Owner: `backend`. Source: XXE Prevention.
- **Remote schema fetched without integrity or authenticated transport.** Integrity-check referenced schema files, bearing in mind the hosting repository could be compromised; when remote schemas are unavoidable, use only encrypted connections, keep certificate and hostname verification on, and stop retrieval when verification fails. HTTPS authenticates the server but does not make a schema safe if the legitimate host or a third-party author is compromised.
  Check: no schema URL uses plain HTTP, TLS verification is not disabled for schema fetches, and pinned local copies or hashes are preferred. Owner: `backend`. Source: XML Security.
- **Local schema or DTD files writable by other users.** A local schema with permissive file permissions lets an internal attacker alter its restrictions.
  Check: images and deploy manifests install schema and DTD files read-only and owned by the service, never world-writable. Owner: `platform`. Source: XML Security.

## Parser-specific XXE settings

- **Java JAXP factories not hardened per API.** Use `newDefaultInstance()` (`newDefaultFactory()` for StAX) to get the built-in implementation, or verify a third-party provider's controls. `DocumentBuilderFactory` and `SAXParserFactory`: set `http://apache.org/xml/features/disallow-doctype-decl` to `true` and `FEATURE_SECURE_PROCESSING`, leave XInclude off, and do not treat `setExpandEntityReferences(false)` as blocking external resources. `XMLInputFactory`: set `SUPPORT_DTD` and `IS_SUPPORTING_EXTERNAL_ENTITIES` to `false` and install an `XMLResolver` that throws (DTD support defaults on and the external-entity default is unspecified; StAX has no secure-processing feature, so use provider limits if DTDs are required). Oracle XDK parsers need `setSecureProcessing()`.
  Check: each factory creation in the diff is followed by these settings before use. Owner: `backend`. Source: XXE Prevention.
- **Java parser that must allow internal DTDs.** Instead of rejecting DOCTYPE, install an `EntityResolver` that throws for external references, set `http://xml.org/sax/features/external-general-entities`, `http://xml.org/sax/features/external-parameter-entities`, and `http://apache.org/xml/features/nonvalidating/load-external-dtd` to `false`, keep XInclude off, set applicable `ACCESS_EXTERNAL_*` properties to `""`, and enable `FEATURE_SECURE_PROCESSING` plus provider processing limits because a resolver does not limit internal entity expansion. DTD validation needs an explicit policy for any required external DTD.
  Check: DTD-enabled parsers carry all of these settings, not only a resolver. Owner: `backend`. Source: XXE Prevention.
- **Secure factory library settings loosened.** Preconfigured factories such as Apache Commons Secure XML do not cover URIs passed directly to parse APIs, parsers created outside the library, or resources your own resolver supplies; do not loosen their reserved security settings.
  Check: code using such a library does not override its reserved features and does not also create raw factories. Owner: `backend`. Source: XXE Prevention.
- **.NET XML parser with DTD processing or a non-null `XmlResolver`.** Below .NET Framework 4.5.2, `XmlDocument`, `XmlTextReader`, and `XPathNavigator` are unsafe by default: set `XmlResolver = null`, set `XmlTextReader.ProhibitDtd = true` (before 4.0) or `DtdProcessing = DtdProcessing.Prohibit` (4.0 and later), and build `XPathNavigator` from an `XPathDocument` over a safe `XmlReader`. At 4.5.2 and later, `XmlDocument` and `XmlTextReader` become unsafe when you supply your own non-null `XmlResolver` with default or unsafe settings, and `XmlReader` when `DtdProcessing.Parse` is combined with such a resolver; if DTD processing is needed, follow Microsoft's safe-DTD guidance.
  Check: no reader or document sets a non-null `XmlResolver` or `DtdProcessing.Parse` for external XML, and pre-4.5.2 targets set the properties above explicitly. Owner: `backend`. Source: XXE Prevention.
- **ASP.NET effective framework below 4.5.2.** The effective .NET version is the lower of the build target and `<httpRuntime targetFramework="..."/>` in `Web.config`; that attribute must be 4.5.2 or higher, and omitting it is unsafe by default. `<compilation targetFramework>` or the project's target framework is not sufficient.
  Check: `Web.config` sets `httpRuntime targetFramework` to 4.5.2 or later. Owner: `backend`. Source: XXE Prevention.
- **libxml2 parse options that enable entities or external DTDs.** Calls such as `xmlReadMemory`, `xmlReadFile`, `xmlReadDoc`, `xmlReadFd`, `xmlReadIO`, `xmlCtxtRead*`, `xmlCtxtUseOptions`, and `xmlParseInNodeContext` must not pass `XML_PARSE_NOENT` or `XML_PARSE_DTDLOAD`; libxml2 2.9 and later disables XXE by default.
  Check: grep libxml2 call sites for those option flags and confirm the linked libxml2 is 2.9 or later. Owner: `backend`. Source: XXE Prevention.
- **Xerces-C parsers using default entity resolution.** Call `setDisableDefaultEntityResolution(true)` on `XercesDOMParser` (with `setCreateEntityReferenceNodes(true)`) and on `SAXParser`, and set `XMLUni::fgXercesDisableDefaultEntityResolution` to `true` on `SAX2XMLReader`; a custom resolver must still reject unapproved resources.
  Check: each Xerces-C parser or reader is configured this way before parsing. Owner: `backend`. Source: XXE Prevention.
- **iOS XML parsing that loads external entities.** iOS up to iOS 6 ships libxml2 older than 2.9, so direct libxml2 use needs the option rules above; for `NSXMLDocument`, specify `NSXMLNodeLoadExternalEntitiesNever` to disable external entities on any iOS version.
  Check: `NSXMLDocument` creation passes `NSXMLNodeLoadExternalEntitiesNever`. Owner: `mobile`. Source: XXE Prevention.
- **PHP libxml options enabling entities without a blocking loader.** Do not enable `LIBXML_NOENT`, `LIBXML_DTDLOAD`, or `LIBXML_DTDVALID` for untrusted XML without blocking external resources; install a `libxml_set_external_entity_loader` callback that returns `null` before processing and keep it installed for that operation. Passing `null` directly to `libxml_set_external_entity_loader()` does not block loading.
  Check: XML parsing of external input runs with a registered callback that returns `null` and without those option flags. Owner: `backend`. Source: XXE Prevention.
- **Python standard-library XML parsers on untrusted input.** Use the `defusedxml` parsing interfaces in place of the corresponding standard-library functions, keep entity and external-resource rejection enabled, and set `forbid_dtd=True` where offered when DTDs are unnecessary; these interfaces reject constructs but do not sanitize XML or replace application resource limits, and higher-level APIs and custom handlers still need an external-resource policy.
  Check: modules parsing external XML import from `defusedxml`, not `xml.etree`, `xml.dom`, `xml.sax`, or `xmlrpc` directly. Owner: `backend`. Source: XXE Prevention.
- **Deployed Python linked to a vulnerable Expat.** Expat below 2.7.2 may be affected by entity-expansion, large-token, or dynamic-memory denial of service, and the Python version alone does not establish the linked Expat version; check `pyexpat.EXPAT_VERSION` in the deployed interpreter and keep Python and Expat updated.
  Check: the runtime image pins a Python and system Expat at or above 2.7.2, verified against `pyexpat.EXPAT_VERSION`. Owner: `platform`. Source: XXE Prevention.
- **ColdFusion XML functions without external entities disabled.** Adobe ColdFusion (2018 Update 14, 2021 Update 4, and later) has no global setting, so every XML function call (`XmlParse`, `XmlSearch`, `XmlTransform`, `isXML`) must pass parser options with `ALLOWEXTERNALENTITIES = false`; Lucee 5.3.4.51 and later sets `this.xmlFeatures` in `Application.cfc` with `externalGeneralEntities: false`, `secure: true`, `disallowDoctypeDecl: true` (disabled by default from 5.4.2.10 and 6.0.0.514).
  Check: every ColdFusion XML call passes the options struct, or Lucee's `Application.cfc` sets the features. Owner: `backend`. Source: XXE Prevention.

## XML denial of service and resource limits

- **Entity expansion left unbounded.** Preventing XXE does not prevent every XML denial of service: recursive entity references, quadratic blowup, and billion-laughs expansion exhaust CPU and memory when a parser processes DTDs without expansion limits.
  Check: parsers that accept DTDs enable secure processing or explicit entity-expansion limits, and parsers that do not need DTDs reject them. Owner: `backend`. Source: XML Security, XXE Prevention.
- **XML parser without size, depth, and decompression limits.** Use a parser that follows the W3C specification and does not take significantly longer on malformed documents, cap document size, nesting depth, element and attribute counts, and decompressed size independently, since deeply nested unclosed elements, jumbo payloads, and decompression bombs (the Python `xmlrpc` module is vulnerable to them) exhaust resources.
  Check: request size and parser limits are configured ahead of parsing, and compressed XML bodies have a decompressed-size cap. Owner: `backend`. Source: XML Security, XXE Prevention.
- **Parser recovery mode used on untrusted documents.** A malformed document is a fatal error: parsing should stop and the document should receive no further processing; recovery modes rebuild trees by unspecified rules that differ between parsers and threaten data integrity.
  Check: parser options for external XML do not enable recover or lenient modes, and parse errors abort the request. Owner: `backend`. Source: XML Security.

## XML document structure and schema strictness

- **XML processed without a strict schema.** Each XML document must have a precisely defined XML Schema (not a DTD) restricting every piece of information, so injected extra elements or duplicated fields are rejected; process only well-formed, valid documents and only values within predefined boundaries.
  Check: inbound XML is validated against an application-owned XSD before business logic, and the schema constrains element order and cardinality. Owner: `backend`. Source: XML Security.
- **Numeric schema types that admit negative, zero, or special values.** Use the narrowest numeric type: `positiveInteger` rather than `integer` for quantities, a type or `assertion` (`$value != 0`) that excludes zero for denominators, and `decimal` rather than `float`/`double` when `INF`, `-INF`, and `NaN` are not needed.
  Check: numeric XSD types match the business domain, with no generic `integer`, `float`, or `double` on prices, quantities, or divisors. Owner: `backend`. Source: XML Security.
- **String schema types without enumeration, length, or pattern.** Restrict fixed sets with `enumeration`, sizes with `minLength`/`maxLength` or `length`, and syntax with `pattern`, and use the specific data type (for example `base64Binary`) rather than a loosely restricted string, ensuring the validator enforces the whole value.
  Check: string-typed XSD elements carry restrictions appropriate to the field. Owner: `backend`. Source: XML Security.
- **Unbounded element occurrences.** `maxOccurs="unbounded"` lets an attacker send extreme numbers of items; analyze the consequences and set a maximum instead.
  Check: schemas in the diff use a numeric `maxOccurs` on repeating elements. Owner: `backend`. Source: XML Security.

## Review and testing

- **No static rule for missing XXE hardening in CI.** Use pre-built or custom static analysis rules to enforce parser hardening, such as the Semgrep rules `documentbuilderfactory-disallow-doctype-decl-missing`, `saxparserfactory-disallow-doctype-decl-missing`, and `xmlinputfactory-possible-xxe`.
  Check: the pipeline's SAST configuration includes XXE rules for the parsers the codebase uses. Owner: `platform`. Source: XXE Prevention.
- **No malformed, oversized, or fuzzed XML in tests.** Compare processing time of a regular document with a malformed version to spot asymmetric resource consumption, test what happens with extremely large numbers of elements, and feed fuzzed XML to expose crashes from specification violations.
  Check: the XML handler's tests include malformed, deeply nested, high-cardinality, and fuzzed inputs with time or resource assertions. Owner: `qa`. Source: XML Security.
