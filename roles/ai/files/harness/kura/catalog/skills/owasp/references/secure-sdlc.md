# Secure SDLC

When to read: the brief, diff, or assessed surface touches a new feature design or architecture change, a threat model or data flow diagram, a change to authentication, sessions, authorization, roles, crypto, secrets, or trust relationships (attack-surface triggers), product security requirements or secure defaults, a security code review, a legacy or end-of-life application, a WAF virtual patch, or a vulnerability disclosure policy, `security.txt`, bug bounty, or security advisory.
Sources (OWASP Cheat Sheet Series, CC BY-SA 4.0): [Threat Modeling](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html), [Attack Surface Analysis](https://cheatsheetseries.owasp.org/cheatsheets/Attack_Surface_Analysis_Cheat_Sheet.html), [Secure Product Design](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Product_Design_Cheat_Sheet.html), [Secure Code Review](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html), [Vulnerability Disclosure](https://cheatsheetseries.owasp.org/cheatsheets/Vulnerability_Disclosure_Cheat_Sheet.html), [Legacy Application Management](https://cheatsheetseries.owasp.org/cheatsheets/Legacy_Application_Management_Cheat_Sheet.html), [Virtual Patching](https://cheatsheetseries.owasp.org/cheatsheets/Virtual_Patching_Cheat_Sheet.html), [Cloud Architecture Security](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Cloud_Architecture_Cheat_Sheet.html)

## Attack surface changes and analysis

- **Attack-surface change shipped without a risk assessment.** Changes to session management, authentication, or password management, to authorization and access-control logic (new or changed roles, new admin users or high-privilege functions), to encryption or secrets handling, to how data validation works, and major architectural changes (layering, trust relationships, swapping the web server, database platform, or OS) need review and threat assessment; a new kind of entry point that fits no existing bucket (a new web service API, an internet file upload) needs a thorough risk assessment. A new user type or role is overlaid across data and functions to find inconsistencies, taking extra care where the access model is allow-by-default rather than deny-by-default.
  Check: diffs touching these areas link a threat-model update or risk note, and new roles come with an explicit data and function access matrix. Owner: `architect`. Source: Attack Surface Analysis, Threat Modeling.
- **Attack surface never mapped.** Map every path for data and commands in and out (UI forms and fields, HTTP headers and cookies, APIs, files, databases, local storage, email and messages, runtime arguments) and the code protecting them, plus the valuable data (secrets and keys, IP, critical business data, PII) and its protections; group entry points by type (login, admin, search, CRUD, workflows, transactional APIs, operational interfaces, integrations) and risk, count them, sample each type, overlay user types with focus on anonymous users and highly privileged admins, and validate by walking main use cases end to end. For microservice and cloud-native systems, prioritize components reachable from attack sources even when behind proxies, load balancers, and ingress.
  Check: an attack-surface inventory exists and lists the entry-point types and counts for the service. Owner: `architect`. Source: Attack Surface Analysis.
- **High-risk code not prioritized for review and testing.** Concentrate review and testing on network-facing (especially internet-facing) code, web forms, files from outside the network, backward-compatible interfaces and old protocols, custom APIs and protocols, and security code (cryptography, authentication, authorization, session management), and know which compensating operational controls (firewalls, WAF, IDS/IPS) protect them.
  Check: the test and review plan names these areas explicitly. Owner: `security`. Source: Attack Surface Analysis.
- **Unused features, versions, and code left deployed.** Multiple deployed versions, features kept "just in case", unused code, and old backup copies enlarge the attack surface; use source control and change management so the deployed surface matches the intended one, and reduce it by simplifying the model (fewer user levels), not storing confidential data you do not need, and turning off unused features and interfaces.
  Check: diffs remove dead endpoints and feature flags rather than leaving them reachable, and no stale copies of the app are deployed. Owner: `backend`. Source: Attack Surface Analysis.
- **Backups left outside the protected surface.** Backups of code and data, online and offline, are part of the attack surface and are protected as strongly as the system they copy.
  Check: backup storage in IaC is encrypted and access-restricted like the primary store. Owner: `cloud`. Source: Attack Surface Analysis.

## Threat modeling

- **Design shipped without a threat model.** Threat model early, ideally at design time, as a standard SDLC step rather than an add-on, and maintain it alongside the system; it answers what are we working on, what can go wrong, what are we going to do about it, and did we do a good enough job. Cloud architectures need risk assessments, threat modeling, and attack-surface assessments that establish threats, their likelihood, the attack surface, and business impact.
  Check: features that add components, data flows, or trust boundaries have a linked, current threat model. Owner: `architect`. Source: Threat Modeling, Cloud Architecture, Secure Product Design.
- **System model without trust boundaries.** Model the system with a data flow diagram (or comparable model, optionally complemented by brainstorming) showing trust boundaries, data flows, data stores, processes, and external entities, saved in a form the team can update, with a high-level overview plus detailed component diagrams for complex systems; for cloud systems include virtual networks, IAM roles, managed services, storage buckets, the shared-responsibility split, ephemeral infrastructure, and compliance and data-residency constraints.
  Check: the model marks every trust boundary the change crosses and lives in the repo or an editable shared location. Owner: `architect`. Source: Threat Modeling.
- **Threats enumerated without a structured method.** Apply STRIDE's six categories to components, data flows, and trust boundaries and record which each threat affects; rank threats by likelihood and impact (optionally including fix effort); use another technique when the scope needs it (attack trees for multi-step attacker goals, misuse or abuse cases for workflow abuse, LINDDUN for privacy harms, PASTA, OCTAVE, VAST), stating why each fits and what it does not cover, and never adding techniques just to look comprehensive.
  Check: the threat list maps each threat to an element of the model and a STRIDE (or other stated) category with a rank. Owner: `architect`. Source: Threat Modeling.
- **Threat without a recorded response.** Every threat gets a response: mitigate, eliminate, transfer (which does not reduce likelihood or harm, so document who owns the remaining controls and residual risk), or accept (with the reason recorded); agreed mitigations become actionable security requirements with an implementation plan, and these decisions stay current as the system changes.
  Check: every threat row has a response, and every mitigation links a requirement or ticket. Owner: `architect`. Source: Threat Modeling.
- **Threat model unreviewed or its mitigations unmeasurable.** All stakeholders, not only developers and security, review whether the model reflects the system, all threats are identified, each has an agreed response, mitigations reduce risk to an acceptable level, the model is formally documented and stored for need-to-know access, and the mitigations can be tested and measured. Invite security specialists to modeling sessions and train teams regularly.
  Check: the threat model records reviewers and states how each mitigation is verified. Owner: `architect`. Source: Threat Modeling.
- **Threat-model mitigations not covered by tests.** Write unit and integration tests that confirm each threat found in threat modeling is mitigated to an acceptable level, and derive use cases and abuse cases for each tier of the application.
  Check: tests exist that exercise each listed mitigation, including abuse cases. Owner: `qa`. Source: Secure Product Design.

## Secure product design

- **Insecure defaults or fail-open behavior.** Establish secure defaults that need minimal manual setup, minimize the attack surface, and design systems to fail into a well-defined secure state rather than exposing vulnerabilities when they malfunction.
  Check: new config options default to the safe value, and error paths in security decisions deny. Owner: `architect`. Source: Secure Product Design.
- **Least privilege or separation of duties missing.** Give users, components, and code only the minimum access needed, and split sensitive transactions so no single individual controls all of their steps.
  Check: service accounts and roles in the change are minimal, and high-impact actions require a second actor where the business process demands it. Owner: `architect`. Source: Secure Product Design.
- **Single layer of defense.** Layer controls (physical, network, application, data) so one failure does not expose the asset, verify every request under a zero-trust model with continuous monitoring and auditing, and put plausibility checks at each tier from frontend to backend.
  Check: the backend re-validates everything the frontend checks, and no control is the only barrier for a high-value asset. Owner: `architect`. Source: Secure Product Design. See `network-zero-trust-and-microservices.md` for zero-trust controls.
- **Product security level never set.** At inception, a business impact assessment sets the product security level from the application's context (who uses it, what data it holds, its risk profile), avoiding both over- and under-engineering; that level drives tier segregation, separation of tenant data or environments, encryption expectations, backup, and data retention. Threat modeling adds security stories in every design iteration.
  Check: the product brief records a security level and the controls it implies. Owner: `architect`. Source: Secure Product Design.
- **Components chosen off the paved road.** Build from secure design patterns and ready-to-use components in the organization's golden path, analyze component choices through threat modeling, review licensing, maintenance, and usage limits, and prefer memory-safe high-level languages recommended there (or manage memory carefully against overflows and use-after-free).
  Check: new libraries or services in the diff are on the approved list or carry a recorded review. Owner: `architect`. Source: Secure Product Design.
- **Secure-coding baseline absent.** Code validates input types, formats, lengths, and business constraints (with parameterized SQL, since validation does not replace parameterization, and separate buffer-bounds enforcement in memory-unsafe components), handles errors without disclosing sensitive information, enforces strong authentication and authorization, protects data in transit and at rest, keeps secrets out of code, runs least-privileged, is security tested during development and before deployment, is audited and reviewed, and stays current with security fixes.
  Check: the definition of done for the change covers these points. Owner: `backend`. Source: Secure Product Design. See `injection.md`, `logging-and-error-handling.md`, and `secrets-management.md` for each control.
- **Images and base systems left unpatched.** Keep software, container images, and base operating systems patched, or build from maintained hardened images.
  Check: base images are on a supported, recently updated tag and an update job exists. Owner: `platform`. Source: Secure Product Design.
- **No practiced incident response plan.** Keep a practiced security incident response plan as part of the product support model, within the broader business continuity plan.
  Check: an incident runbook exists for the product with escalation contacts and has been exercised. Owner: `sre`. Source: Secure Product Design, Legacy Application Management.

## Security code review

- **Security review missing from the change workflow.** Run diff-based security review on pull requests, lightweight pre-commit checks, feature completion, sprint reviews, hotfixes, and CI-triggered reviews, and baseline (whole-codebase) reviews at project initiation, before major releases, on architecture changes, for compliance cycles, after security incidents, and when onboarding legacy systems; escalate from diff to baseline review when significant concerns appear.
  Check: the PR process includes a security review step and a record of baseline reviews exists for major releases. Owner: `security`. Source: Secure Code Review.
- **Diff reviewed without assessing control impact.** Before reviewing, understand the change's purpose, the architecture, threat models, and previous findings; then analyze impact on existing security controls, identify new attack vectors, verify security at modified trust boundaries, check new integrations, confirm no security regression, and prioritize high-risk modifications. Baseline reviews add architecture anti-pattern review, entry points, authentication and authorization, data flow, business logic, crypto, error handling, configuration and deployment, and an audit of all third-party libraries.
  Check: review notes for security-relevant diffs mention the controls and trust boundaries touched. Owner: `security`. Source: Secure Code Review.
- **Data not traced from source to sink.** Trace sources (user input, uploads, API calls, database reads, environment variables) through processing to sinks (queries, file writes, rendering, logging, external APIs), verify validation and output encoding at each trust boundary crossing, and confirm sensitive data gets protection matching its classification; review workflows for state-transition validation, step bypass, authorization at every step, race conditions (TOCTOU, requiring atomic operations), transaction rollback, resource limits, concurrent access, and boundary conditions.
  Check: for each new sink in the diff, the review identifies its sources and the control between them. Owner: `security`. Source: Secure Code Review. See `abuse-dos-and-business-logic.md` for business-logic abuse.
- **Automated findings used without human triage, or review unmanaged.** Run SAST and dependency scanning before manual review and use the results to prioritize, apply human judgment to filter false positives, focus manual effort where tools are weak (business logic, authorization models, race conditions, crypto misuse, architecture); use standardized checklists and finding templates (title, severity, CWE, location, impact, reproduction, recommendation, status, assignee, due date), keep a knowledge base of common issues, track review metrics (coverage of critical paths, finding quality, trends), and train reviewers and security champions.
  Check: CI runs SAST and dependency scans, and security findings are tracked with severity, CWE, and owner. Owner: `security`. Source: Secure Code Review.
- See `injection.md` for the review checklist's input-validation items (server-side allowlist validation, parameterized queries, length limits, Unicode handling).
- See `sessions-and-cookies.md` for the checklist's session items (at least 128 bits of token entropy, invalidation on logout and timeout, `HttpOnly`, `Secure`, `SameSite`, concurrent-session limits).
- See `cryptography-and-keys.md` for the checklist's crypto items (AES-256, RSA-2048 or larger, ECDSA P-256 or larger, unpredictable CBC IVs, GCM IVs unique per key, CSPRNG use, hostname-verified certificates).
- See `authorization.md` for the checklist's authorization items (server-side enforcement, default deny, IDOR prevention, centralized decisions, role tampering, privilege escalation).

## Legacy applications

- **Legacy application not inventoried or risk-assessed.** Document every legacy application with version, production date, relevant configuration, the network hosts needed to reach it, services running on its infrastructure, and where relevant physical location and permitted access (optionally an SBOM); assess its risk and threats down to components such as API routes and open ports, considering the data it handles, known and exploitable vulnerabilities, availability criticality, and whether compromising it opens a path to privileged networks or other data.
  Check: the legacy inventory entry and risk assessment exist and name exposed routes and ports. Owner: `architect`. Source: Legacy Application Management.
- **Legacy application broadly reachable.** Treat legacy applications as inherently high risk: host them in a restricted subnet with IP allowlisting (or air-gapped when needed), disable high-risk and administrative features users do not need, require authentication to the application (itself or through an IdP) and to its network environment, close unneeded ports and restrict the rest with firewall rules, and where possible front it with an intermediary API so users never touch it directly; when it only speaks plaintext protocols, apply the most restrictive network controls possible, up to air-gapping, and otherwise encrypt its data at rest and in transit.
  Check: network config admits the legacy host only from named sources on required ports, and authentication sits in front of it. Owner: `cloud`. Source: Legacy Application Management. See `network-zero-trust-and-microservices.md` for proxy and protocol-translation patterns.
- **Legacy vulnerabilities neither scanned nor prioritized.** Scan legacy applications on an automatic schedule with an industry-standard vulnerability scanner, add SAST and SCA where possible, and fall back to manual host and code review otherwise; patch confirmed vulnerabilities prioritized by exposure, criticality, impact, exploitability, and evidence of active exploitation (the CISA KEV catalog is one input), never by the mere presence or absence of a CVE; where patching is impossible, add access restrictions.
  Check: a scheduled scan job covers the legacy host, and remediation tickets record the prioritization inputs. Owner: `platform`. Source: Legacy Application Management.
- **Legacy knowledge or exit plan missing.** Train more than one person to troubleshoot and reconfigure the application, document processes and troubleshooting guides, teach a core group its language if needed, and keep a migration plan with granular steps, an explicit completion date, and a stated business and security case, built with the people who run and use it.
  Check: the runbook names at least two maintainers and a dated migration plan exists. Owner: `architect`. Source: Legacy Application Management.
- **Legacy application under-monitored.** Monitor legacy applications especially closely: build custom APIs or scripts to convert their logs into a format the SIEM ingests or to report indicators of compromise, watch for anomalous traffic and surges, have incident responders prioritize them, and document downtime and compromise procedures with escalation contacts in an incident playbook.
  Check: the legacy app's logs reach the SIEM (directly or via a converter) and an alert exists for traffic anomalies. Owner: `sre`. Source: Legacy Application Management.

## Virtual patching

- **Virtual patch treated as the fix.** A virtual patch only blocks recognized exploit variants in traffic the enforcement layer inspects and does not remove the vulnerability, so the code or vendor fix continues in parallel, business owners are told it is risk reduction, the patch is tracked in normal patch management with change tickets and rule IDs, and periodic reassessment decides when to retire it.
  Check: every WAF virtual-patch rule references a ticket for the real fix and a rule ID. Owner: `cloud`. Source: Virtual Patching.
- **Exploit-specific virtual patch.** Prefer a positive-security (allowlist) patch that defines valid input for the affected parameter (character set, length, parameter count) from audit logs, use negative rules only knowing they are faster but more evadable, never block just the reported payload, confirm virtual patching suits the flaw (it fits injection-type flaws best), and test alternate encodings, all affected endpoints, and paths that bypass the enforcement layer before claiming coverage; evasion during retest sends the work back to analysis.
  Check: the rule constrains the parameter's allowed format rather than matching a payload string, and its tests include encoding variants. Owner: `cloud`. Source: Virtual Patching.
- **Virtual patch switched straight to blocking.** Pre-authorize an expedited review and rollout process, test both exploit attempts and legitimate workflows (false positives block valid transactions), define monitoring and rollback criteria before blocking, deploy first in log-only mode, and ask whoever found the vulnerability to retest.
  Check: new virtual-patch rules land in detection or log-only mode with a documented rollback before switching to block. Owner: `cloud`. Source: Virtual Patching.
- **Virtual patching capability not prepared.** Before an incident, subscribe to vendor vulnerability alerts for commercial software in use, deploy the virtual patching tool in advance so it can be enabled quickly, and configure HTTP audit logging that records rule ID, timestamp, endpoint, enforcement outcome, and correlation ID while excluding or redacting query strings, headers, cookies, and bodies that may hold passwords or payment data; run reports on when virtual patches trigger.
  Check: WAF logging config records rule outcomes without full request capture. Owner: `cloud`. Source: Virtual Patching.
- **Vulnerability handled without tracking data.** Record each vulnerability in the ticketing system with its public identifier (CVE) or an internally assigned one, its impact level, affected versions, triggering configuration, and available proof-of-concept payloads for building and testing the patch; custom applications rely on proactive identification (assessments and source review) because no vendor will warn about them.
  Check: the vulnerability ticket carries these fields. Owner: `security`. Source: Virtual Patching.

## Vulnerability disclosure

- **No published way to report vulnerabilities.** Publish a clear, secure reporting channel: a security contact on the contact page, reporting instructions in the bug tracker, a `security@` address, and `/.well-known/security.txt` per RFC 9116 with at least the required `Contact` and `Expires` fields (optionally `Preferred-Languages`, `Canonical`, `Policy`, `Hiring`); provide reporting guidelines (information wanted, confidential issue category, PGP key, response and triage timeline, safe harbor), and make sure frontline staff know how to escalate security reports.
  Check: `security.txt` is served with `Contact` and an unexpired `Expires`. Owner: `security`. Source: Vulnerability Disclosure.
- **Reporters left without response or threatened.** Respond within a reasonable timeline: acknowledge, give a triage timeline, ask for clarification, confirm and give a fix timeline (with any reward), request retest, and confirm resolution, with regular status updates throughout; never threaten legal action, route payment-demanding reporters through a mediated bug bounty platform, and offer rewards and credit (non-monetary options such as discounts, swag, or a hall of fame when money is not possible).
  Check: the disclosure policy states response timelines and a no-legal-action commitment. Owner: `security`. Source: Vulnerability Disclosure.
- **Fixed vulnerability without a findable advisory.** Publish a security advisory that at minimum gives a summary with impact, vulnerable versions, patched versions, configuration caveats, workarounds, and the CVE ID (requested from the appropriate CNA), ideally with timeline, researcher credit, technical details, and IDS/IPS signatures or indicators of compromise, published on a security page or mailing list and linked from changelogs and release notes; for private systems, weigh publication carefully, possibly with legal advice.
  Check: release notes for a security fix link an advisory containing these fields. Owner: `security`. Source: Vulnerability Disclosure.
- **Bug bounty launched without maturity or defined scope.** Run a bug bounty only on top of a mature disclosure process and strong internal remediation, and define in-scope systems (live or staging, excluding third-party systems), eligible vulnerability types, safe-harbor terms (with legal advice), reward amounts and how they are decided, and timelines for response, confirmation, payout, and resolution.
  Check: the program brief documents each of these. Owner: `security`. Source: Vulnerability Disclosure.
- **Security testing outside authorized scope.** Testing is legal and authorized, stays within the program's scope and rules, respects others' privacy, redacts personal data from reports, uses an encrypted channel where available, and never makes payment a condition of disclosure.
  Check: the red-team or test plan records authorization and scope. Owner: `security`. Source: Vulnerability Disclosure.
