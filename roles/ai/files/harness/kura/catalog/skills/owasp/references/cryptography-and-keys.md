## Randomness

- **Non-cryptographic PRNG used for a security value.** Keys, IVs, session ids, CSRF tokens, and password reset tokens come from a CSPRNG; PRNGs such as `Math.random()`, `java.util.Random`, `ThreadLocalRandom`, `mt_rand()`, `rand()`, `uniqid()`, `lcg_value()`, Python `random`, Go `math/rand`, .NET `Random()`, and Ruby `rand()` must not be used for anything security critical.
  Check: grep the diff for PRNG calls on any path that produces a secret, token, nonce, or key; replace with the platform CSPRNG (for example `SecureRandom`, `secrets`, `crypto.randomBytes`/`randomInt`/`randomUUID`, `crypto/rand`, `random_bytes`/`random_int`, `RandomNumberGenerator`, `getrandom`). Owner: `backend`. Source: Cryptographic Storage.
- **UUID relied on as an unpredictable secret.** Version 1 UUIDs are a timestamp plus MAC address and are not random; version 4 randomness depends on whether the implementation uses a CSPRNG, so UUID randomness is not relied upon unless known secure for the specific language or framework.
  Check: flag UUIDs used as reset tokens, API keys, or capability URLs; confirm v4 from a documented CSPRNG source or switch to a CSPRNG token. Owner: `backend`. Source: Cryptographic Storage.

## Algorithms, modes, and padding

- **Custom or home-grown cryptographic algorithm.** Do not create custom algorithms; use only reputable, well-maintained libraries that are tested and validated by third parties (for example NIST/FIPS).
  Check: flag hand-written cipher, MAC, or KDF code and unmaintained crypto dependencies. Owner: `backend`. Source: Cryptographic Storage, Key Management.
- **Symmetric encryption below AES-128 or in an unauthenticated mode.** Symmetric encryption uses AES with at least a 128-bit key (ideally 256) in an authenticated mode, GCM or CCM first (AES-256-GCM or ChaCha20-Poly1305 for secrets); CTR or CBC are used only when GCM/CCM are unavailable and then with separate Encrypt-then-MAC authentication (with care for variable-length messages); ECB is not used outside very specific circumstances.
  Check: find cipher constructors in the diff; flag DES/3DES/RC4, ECB, and CBC/CTR without an Encrypt-then-MAC step, and confirm IVs are generated by the library. Owner: `backend`. Source: Cryptographic Storage, Secrets Management.
- **Public-key encryption built from primitives instead of a hybrid scheme.** Public-key encryption uses a maintained library implementing an established hybrid scheme such as HPKE; X25519 is a key-agreement primitive that does not encrypt data by itself, and the HPKE base mode does not authenticate the sender, so an authenticated mode is selected when sender authentication is required.
  Check: flag code that uses raw X25519 or ECDH output as an encryption key without a KDF and AEAD; where sender identity matters, confirm an HPKE auth mode. Owner: `backend`. Source: Cryptographic Storage.
- **RSA below 2048 bits or without OAEP.** If RSA must be used, keys are at least 2048 bits and encryption uses a maintained library's RSAES-OAEP (RFC 8017 Section 7.1); RSA without an encryption padding scheme, or with ad hoc random bytes prepended, is not acceptable.
  Check: flag key generation below 2048 bits and RSA encryption with no padding or a padding other than OAEP. Owner: `backend`. Source: Cryptographic Storage.
- **Key strength not tied to the data's protection lifetime.** The application establishes its minimum computational resistance from adversary sophistication, how long data must be protected, and where it is stored, and derives key lengths from NIST SP 800-57 and SP 800-131A; elliptic-curve key lengths meet or exceed the comparative strength of other algorithms in the system.
  Check: confirm the design or config documents a minimum security strength and that all key sizes in use meet it. Owner: `architect`. Source: Key Management.
- **No plan to swap algorithm or library.** Processes are in place to change the encryption algorithm or library quickly if a vulnerability is found in it.
  Check: confirm algorithm identifiers are configurable or versioned in stored ciphertext metadata rather than hard-coded throughout. Owner: `backend`. Source: Cryptographic Storage.
- **Algorithm chosen without selection criteria or regulatory constraints.** Algorithm choice weighs key size, known attacks, maturity, third-party approval (NIST CAVP), performance, library quality, and portability, and respects regulatory limits such as FIPS 140-3 or PCI DSS.
  Check: where the system is in a regulated scope, confirm the chosen algorithms and modules are on the approved list. Owner: `architect`. Source: Cryptographic Storage.
- See `http-headers-tls-and-caching.md` for ephemeral key exchange and perfect forward secrecy in TLS.

## Key storage, wrapping, and separation

- **Key material in source, version control, build artifacts, or environment variables.** Keys are never hard-coded, committed, or embedded in binaries, container images, or configuration files; they live in a dedicated secrets manager or key vault, configuration files that must hold keys get restrictive permissions, and environment variables are avoided because they leak through diagnostics and `/proc/self/environ`.
  Check: scan the diff for key literals, PEM blocks, and key files; confirm keys are fetched from a vault or KMS at runtime. Owner: `backend`. Source: Cryptographic Storage, Key Management.
- **Application code handles raw key material.** Where available, keys are held in an HSM, virtual HSM, cloud KMS, or secrets service, and all cryptographic operations (generation, encryption, decryption, signing) run inside that module boundary so plaintext keys are never exposed to application code; higher-assurance deployments (ASVS Level 3) use hardware-backed modules (HSM or TPM).
  Check: flag code that exports or reads plaintext key bytes from a vault to encrypt locally when the module could perform the operation. Owner: `backend`. Source: Cryptographic Storage, Key Management.
- **Keys stored alongside the data they protect.** Keys are stored in a separate location from encrypted data (for example data in the database, keys on the filesystem or another system) so a single SQL injection or traversal does not yield both; keys are never stored next to the secrets they encrypt unless themselves encrypted.
  Check: confirm the key source is a different system or store from the ciphertext; flag key columns in the same database as the encrypted data. Owner: `backend`. Source: Cryptographic Storage, Secrets Management.
- **Stored keys not wrapped by a separate KEK.** Keys are stored encrypted: a DEK encrypts data and a KEK, stored separately and at least as strong as the DEK, encrypts the DEK; keys exported to offline devices or databases are wrapped with a KEK of equal or greater strength first, and keys are never stored in plaintext.
  Check: confirm envelope encryption (wrapped DEK stored with data, KEK in KMS/HSM) and compare KEK and DEK strength. Owner: `backend`. Source: Cryptographic Storage, Key Management.
- **Stored keys lack integrity protection.** Keys in storage carry integrity protection (an authenticated wrapping scheme, MAC, or signature) so modification or substitution of the key or its associations is detected.
  Check: confirm the key-wrap mechanism is authenticated (AEAD or encrypt-plus-MAC) rather than plain encryption. Owner: `backend`. Source: Key Management.
- **Passphrase-derived KEK not used where user-controlled keys are needed.** A KDF can derive the KEK from a user passphrase to wrap a random DEK, so a passphrase change rewraps the DEK without re-encrypting data.
  Check: where user passphrases protect data, confirm the passphrase feeds a KDF to a KEK and never directly encrypts data. Owner: `backend`. Source: Cryptographic Storage.
- **Key locations unknown to the developers.** Developers know where keys are stored and on which memory devices, and keys are protected in both volatile and persistent memory.
  Check: confirm a key inventory or design note names each key's storage location. Owner: `architect`. Source: Key Management.

## Key generation and usage

- **Keys derived from words, phrases, or human input.** Keys are generated by a cryptographically secure function, never from common words, phrases, or keyboard mashing, and multiple keys (such as DEK and KEK) are fully independent.
  Check: flag keys produced by hashing a constant string or from a config value typed by a human. Owner: `backend`. Source: Cryptographic Storage.
- **Keys generated outside a validated module.** Keys and their random inputs are generated within a FIPS 140-2 or 140-3 compliant cryptographic module (hardware modules preferred), and transported only over secure channels for use in such modules.
  Check: confirm generation happens in the KMS/HSM or a validated library mode, and that key distribution uses an encrypted, authenticated channel. Owner: `cloud`. Source: Key Management.
- **One key used for several purposes.** A key serves one purpose only (encryption, authentication, key wrapping, random generation, or signing), since mixing weakens the processes and widens the blast radius of compromise.
  Check: flag the same key id or secret referenced by both encryption and signing or MAC code paths. Owner: `backend`. Source: Key Management.

## Rotation and cryptoperiods

- **No rotation capability ready before it is needed.** The code and processes to rotate a key exist before a compromise, triggered by suspected compromise (including someone with access leaving), the end of the cryptoperiod, approaching the mode's usage limits, or a significant new attack; formal, tested processes cover generation, distribution, deployment, rotation, and decommissioning.
  Check: confirm ciphertext records the key id or version and that a rotation path (new key for new writes, old keys for reads) exists in code. Owner: `backend`. Source: Cryptographic Storage, Key Management.
- **AES-GCM key exceeds its usage limits.** Rotation accounts for usage volume as well as time: with random 96-bit IVs a key encrypts at most 2^32 messages across all instances sharing it, and the mode's message-size and IV-uniqueness limits are enforced across every instance.
  Check: for high-volume GCM use, confirm either deterministic IV construction with uniqueness guarantees or a per-key operation counter and rotation trigger. Owner: `backend`. Source: Cryptographic Storage, Key Management.
- **Cryptoperiods undefined or outside the published ranges.** A documented rotation schedule derives from risk assessment per NIST SP 800-57; representative values are symmetric DEK originator use up to 2 years for low-volume systems (a day or a week for high-volume or link encryption) with recipient use no more than 3 years beyond, private signing keys 1 to 3 years, static key-agreement pairs 1 to 2 years, and ephemeral pairs a single transaction.
  Check: confirm KMS rotation periods or a rotation runbook state cryptoperiods per key type within these ranges. Owner: `cloud`. Source: Key Management.
- **Rotation done by hand or without an audit trail.** Automated rotation through KMS or ACME is preferred; when manual rotation is required, each event is logged with timestamp, operator identity, and management authorization reference.
  Check: confirm automatic rotation is enabled on managed keys and certificate issuance is automated; for manual paths, confirm the log fields. Owner: `cloud`. Source: Key Management.
- **Certificate renewal assumed to replace the key pair.** TLS certificate renewal is planned around CA/Browser Forum Baseline Requirements validity limits, and key replacement is scheduled separately because renewal does not necessarily generate a new key.
  Check: confirm renewal automation generates a fresh key or that a separate key-replacement schedule exists. Owner: `cloud`. Source: Key Management.
- **Old data left under a retired key, or KEK destroyed before rewrapping.** Existing data is preferably decrypted and re-encrypted under the new key, otherwise each item is tagged with its key id and old keys are retained (also for backups); retiring a KEK requires rewrapping every DEK first, rewrapping does not reset DEK cryptoperiods or usage counts, and replacing a DEK requires re-encrypting its data.
  Check: read the rotation job; confirm it rewraps all DEKs before disabling the old KEK version and handles backups. Owner: `backend`. Source: Cryptographic Storage, Key Management.

## Backup, compromise, and destruction

- **No secure key backup for long-lived encrypted data.** Data under a lost key is unrecoverable, so the application has a secure key backup capability with the key backup store encrypted by a FIPS 140-2/140-3 validated module; encryption keys may be escrowed, signing keys are never escrowed.
  Check: confirm a backup or multi-region replica exists for data keys, and that no signing key is exported to escrow. Owner: `cloud`. Source: Key Management.
- **No documented key compromise-recovery plan.** A compromise-recovery plan is documented and accessible, naming who to notify and who performs recovery, the re-key method, an inventory of all keys and their uses, enforced revocation checking, monitoring of re-keying, and procedures to identify affected data and invalid signatures.
  Check: confirm a runbook exists in the repo or linked docs with these elements. Owner: `sre`. Source: Key Management.
- **Plaintext key exposure not minimized.** Time in plaintext is limited, humans are prevented from viewing plaintext symmetric and private keys, plaintext keys stay in physically protected containers, key confirmation is used when establishing keys, and trusted timestamps are used for signed data.
  Check: flag scripts or tooling that print, export, or copy plaintext keys for humans. Owner: `cloud`. Source: Key Management.
- **Compromised or retired keys not revoked and destroyed.** Compromised keys are revoked promptly and stop protecting new data; all copies of secret and private keys (backup, archive, escrow, memory) are destroyed once no longer needed and retention is satisfied, while public verification keys may be retained for archived signatures; policies cover the NIST SP 800-57 lifecycle states.
  Check: confirm key states (active, deactivated, compromised, destroyed) are modeled and a destruction step exists for every copy. Owner: `cloud`. Source: Key Management.
- **Crypto-erasure relied on while copies remain.** Cryptographic erasure is used only when all copies of the protecting keys can be destroyed and no recoverable plaintext copies remain; destroying a wrapping key does not erase plaintext copies of what it protected.
  Check: before accepting crypto-shredding as deletion, confirm no plaintext caches, exports, or backups of the data or DEKs exist. Owner: `data`. Source: Key Management.
- **Key material not zeroized on disposal.** Overwriting keys is best-effort in managed runtimes, so platform secure-memory or zeroization APIs are used where available; HSM keys are cleared with vendor zeroize commands, and obsolete media or tokens holding keys are physically destroyed.
  Check: confirm key buffers use mutable byte arrays cleared after use or a secure-memory API. Owner: `backend`. Source: Key Management.

## Access, accountability, and trust stores

- **Broad access to keys and key management interfaces.** Least privilege applies to every key and secret asset: only authorized roles, services, and workloads with a verified need can use keys or the key management interface.
  Check: read KMS key policies and IAM grants; flag wildcard principals or actions such as `kms:*` on application roles. Owner: `cloud`. Source: Key Management.
- **No accountability for who can see or use keys.** The key management system accounts for everyone able to view plaintext keys (ideally no one), uniquely identifies keys and their users, records dates and times of use with the data protected, and tracks which keys protect other keys; plans and protective mechanisms are audited periodically and unusual events reviewed.
  Check: confirm key-use audit logging (for example KMS data events) is enabled and retained. Owner: `cloud`. Source: Key Management.
- **Trust store writable or exportable without control.** The trust store is protected against injection of third-party root certificates, has integrity controls on stored objects, forbids key export without authentication and authorization, has strict export policies, and is updated through a secure process.
  Check: flag code or images that append CAs to the trust store at runtime or disable certificate verification, and confirm who can modify the trust bundle. Owner: `platform`. Source: Key Management.

## Design and data minimization

- **Sensitive data stored when it need not be.** The best protection is not storing sensitive information at all (especially payment card data), so storage of sensitive data is avoided wherever possible.
  Check: for each new sensitive column or field, confirm a requirement for retaining it. Owner: `architect`. Source: Cryptographic Storage.
- **Encryption layer chosen without a threat model.** The layer (application, database, filesystem, hardware) follows the threat model, since hardware or disk encryption protects only against physical theft and not remote compromise; managed key or secret services are used where available.
  Check: confirm the design states which attacker the chosen encryption layer defends against. Owner: `architect`. Source: Cryptographic Storage.
- **Encryption treated as the only control.** Applications remain secure if cryptographic controls fail: encrypted data still has access control, and encrypted URL parameters are not relied upon for security.
  Check: flag object access gated only by an encrypted id or parameter with no authorization check. Owner: `backend`. Source: Cryptographic Storage.
- **No organization-wide cryptographic strategy or component map.** An organizational crypto strategy sets minimum requirements, and each application identifies its crypto requirements and maps every component that processes or stores key material.
  Check: confirm a key and algorithm inventory exists for the system. Owner: `architect`. Source: Key Management.
- See `authentication.md` for password storage; passwords are hashed, never reversibly encrypted.
- See `secrets-management.md` for secrets handling in memory and the secret lifecycle.

## Post-quantum migration

- **No cryptographic inventory.** A cryptographic inventory has one entry per use of cryptography, including platform and provider-managed dependencies, recording purpose and protection lifetime, protocol, algorithms and parameters, library versions, key and certificate ids (metadata only, never key material), dependencies, and an owner; each transport hop (including gateway to application) is mapped separately, stored-data key protection is traced, and signature verifiers are inventoried as well as signers.
  Check: confirm the inventory exists and every entry has an owner and a migration path or recorded blocker. Owner: `architect`. Source: Post-Quantum Cryptography.
- **Migration not prioritized by protection lifetime.** Data that must stay confidential for years and long-lived trust (firmware verification, trust anchors, signed records) are prioritized, each item has an owner and target date, and blocked dependencies record the remaining exposure, a review date, and whether replacement is needed.
  Check: confirm the backlog separates confidentiality from signature work and has explicit decisions for blocked dependencies. Owner: `architect`. Source: Post-Quantum Cryptography.
- **Long-lived data keys protected only by classical public-key crypto.** RSA and ECC (including Curve25519) are not post-quantum secure; AES-256 is preferred for extra margin (AES-128 remains permitted), and the public-key protection of stored encryption keys, including existing wrapped keys, is part of the migration through the provider's supported process while retaining recovery access.
  Check: trace how each data key is wrapped; flag RSA or ECC wrapping of keys for long-retention data without a migration item. Owner: `architect`. Source: Cryptographic Storage, Post-Quantum Cryptography.
- **Post-quantum key establishment hand-assembled.** Key establishment uses a supported integration of ML-KEM (FIPS 203), typically hybrid with a classical algorithm; ML-KEM establishes a shared secret and neither encrypts data nor authenticates the peer, and hybrids come from the protocol's implementation, never a custom combination.
  Check: flag code that combines classical and PQC outputs by hand; confirm a library or protocol-provided hybrid. Owner: `backend`. Source: Cryptographic Storage, Post-Quantum Cryptography.
- **Hybrid TLS assumed to make certificates quantum-safe.** Transport pilots a supported hybrid such as X25519MLKEM768 with certificate and hostname validation kept enabled; hybrid key exchange does not make classical certificate signatures quantum-resistant.
  Check: confirm TLS config adds the hybrid group without disabling verification. Owner: `platform`. Source: Post-Quantum Cryptography.
- **Signature migration accepts either signature.** Signatures migrate separately (for example ML-DSA, FIPS 204) with coordinated signer and verifier upgrades; where a dual-signature scheme requires both, both verifications are enforced, and no custom signature field is appended to an existing token or certificate format.
  Check: in verification code, confirm both signatures are required and a missing one causes rejection. Owner: `backend`. Source: Post-Quantum Cryptography.
- **Long-term signed records lose provability.** Signed records needing long-term proof are validated and preserved through a supported archive timestamp and renewal process before their algorithms weaken; keeping an old verifier alone does not preserve proof.
  Check: confirm an archive-timestamp renewal process exists for such records. Owner: `architect`. Source: Post-Quantum Cryptography.
- **PQC rollout untested on the real path.** Tests use the actual algorithms and parameter sets, exercise real clients, proxies, gateways, and backends, verify the negotiated key exchange (including resumed TLS sessions), check certificate, signature, message, and database field size limits explicitly, test rejection of invalid signatures, untrusted certificates, and disallowed algorithms, and test existing data, older signed artifacts, backup restore, and key recovery before old keys retire.
  Check: confirm tests cover rejection cases and that size limits are explicit config values. Owner: `qa`. Source: Post-Quantum Cryptography.
- **Silent fallback to classical-only protection.** Where PQC is required, failures do not silently retry classical-only; the operation pauses instead, a rollback to classical-only is a security exception with an owner and expiry, and classical-only exceptions are limited to identified legacy artifacts, never new ones.
  Check: flag retry or negotiation code that downgrades on failure without policy; confirm exceptions are recorded with expiry. Owner: `backend`. Source: Post-Quantum Cryptography.
- **Rollout not observed.** Rollout is staged with an approved rollback plan, negotiated algorithms and verification outcomes are recorded without logging secrets, unexpected classical-only use and verification failures alert, and library updates and standards are tracked while the inventory stays current.
  Check: confirm metrics or logs capture the negotiated group and verification result, and an alert rule exists for classical-only use. Owner: `sre`. Source: Post-Quantum Cryptography.
