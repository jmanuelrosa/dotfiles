# File Upload

When to read: the brief, diff, or assessed surface touches a file or attachment upload endpoint, multipart parsing, storage of user-supplied files (disk, bucket, database), image or document processing, archive extraction, filename handling, or serving uploaded files back to users.
Sources (OWASP Cheat Sheet Series, CC BY-SA 4.0): [File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## Storage location and execution

- **Uploaded files stored where the web server can execute or serve them.** Files are stored, in order of preference, on a different host, else outside the webroot with only administrative access, else inside the webroot with write-only permissions and read access gated by explicit controls (internal IP, authorized user).
  Check: find the storage path or bucket for uploads; flag any path under the served document root or a bucket/prefix that is publicly readable without an access check. Owner: `backend`. Source: File Upload.
- **Uploaded files served directly by their stored name.** Public retrieval goes through a handler that maps an application id to the file (`someid -> file.ext`), and downloads never reference the original user filename.
  Check: confirm download routes look files up by an opaque id and set the response filename from validated metadata, not by joining a request parameter onto a directory path. Owner: `backend`. Source: File Upload, Logging Vocabulary.
- **Upload directory honours per-directory server configuration.** An uploaded `.htaccess` or `web.config` can remap a harmless extension to an interpreter, so per-directory configuration overrides are disabled on upload directories (for example `AllowOverride None`, locked IIS handler mappings) in addition to storing outside the webroot.
  Check: read the web server config for the upload location; confirm overrides are disabled and that `.htaccess`/`web.config` filenames are rejected at upload. Owner: `backend`. Source: File Upload.
- **Stored files carry broader filesystem permissions than needed.** Files are stored under least privilege: only the allowed system users can read them and only the required modes are set; if execution is genuinely required, the file is scanned for macros or hidden scripts before it runs.
  Check: inspect the mode/ACL applied on write (umask, explicit chmod, bucket ACL); flag execute bits or world-readable modes. Owner: `backend`. Source: File Upload.
- **Database chosen as file store without the trade-offs addressed.** Storing files in a database is advised only when a DBA is on the team and it proves an improvement over the filesystem, since it adds performance, backup-size, and SQL injection exposure.
  Check: if uploads go into a database column, confirm parameterized writes and a size cap, and that the choice is recorded. Owner: `database`. Source: File Upload.
- **Files emailed or processed without being stored skip the controls.** Files that are mailed on or processed once and never stored still go through every validation in this file before any action is taken on them.
  Check: trace upload handlers that forward or transform the file immediately; confirm the same validation pipeline runs first. Owner: `backend`. Source: File Upload.

## Filename handling

- **User-supplied filename used as the stored filename.** The stored filename is a random string generated by the application (for example a UUID); this also defeats overwrite of existing files and Windows 8.3 short-name aliasing, because the attacker no longer chooses which file is targeted.
  Check: confirm the write path is built from a server-generated name, never from the multipart filename; flag any join of the upload directory with the client-supplied original name. Owner: `backend`. Source: File Upload.
- **Business-required user filenames not constrained.** When the original name must be kept, it has a maximum length suited to the storage system, an allowed character subset (alphanumerics, hyphen, space, period), no leading period (hidden files), no sequential periods (traversal), and no leading hyphen or space (shell safety); if an allowlist is impossible, dangerous characters are blocklisted, and users are told what an acceptable filename is.
  Check: read the filename validator; confirm length cap, allowlisted charset, and the leading-character and `..` rules, and that it is applied server side. Owner: `backend`. Source: File Upload.
- **Colon accepted in filenames on Windows hosts.** NTFS Alternate Data Streams (`shell.asp:.jpg`, `::$DATA`) create a file with the extension before the colon, so any filename containing `:` is rejected.
  Check: confirm the filename validator rejects `:`. Owner: `backend`. Source: File Upload.
- **Overwrite check compares only the long filename on NTFS.** A predictable 8.3 short alias of an existing sensitive file can bypass an exact-name check; server-generated names remove the risk, and disabling short-name creation does not remove existing aliases, which must be assessed separately.
  Check: on Windows storage, confirm names are server-generated, or that collision checks resolve the canonical path rather than comparing strings. Owner: `backend`. Source: File Upload.

## File type validation

- **Extension not validated against an allowlist of business-critical types.** Only the extensions the feature needs are allowed, choosing the least harmful, lowest-risk types (for example one agreed image type for images, `docx` and `pdf` for CVs); blocking known-bad extensions is weak on its own.
  Check: find the extension check; flag denylist-only logic and allowlists broader than the feature requires. Owner: `backend`. Source: File Upload.
- **Extension check bypassable by decoding or naming tricks.** Validation runs after input validation and after the filename is decoded, and handles double extensions (`.jpg.php`), null bytes (`.php%00.jpg`), case changes (`.pHp`), and alternative interpreter extensions (`.phtml`, `.php5`, `.pht`, `.jspx`, `.aspx`); hand-rolled regex logic is avoided unless well tested and reviewed.
  Check: confirm the extension is taken from the final segment after decoding and lowercased, that null bytes are rejected, and that the regex is anchored to the end of the name. Owner: `backend`. Source: File Upload.
- **Client Content-Type header trusted as the file type.** The `Content-Type` is user-controlled and trivially spoofed; it is used only as a quick sanity check (preferably against an allowlist), never as the security decision.
  Check: flag any branch that accepts or routes a file solely on the request's MIME type. Owner: `backend`. Source: File Upload.
- **File signature check used as the only type control.** Magic-byte validation complements content-type validation but is easy to bypass and is never used alone.
  Check: confirm signature checks are combined with the extension allowlist and content validation. Owner: `backend`. Source: File Upload.

## Content validation and malware

- **Images stored as uploaded.** Images are decoded and re-encoded to an allowed format with unnecessary metadata stripped; the image processor handles untrusted input, so it is kept up to date and run with restricted formats, resource limits, and sandboxing.
  Check: confirm a re-encode step exists and that the processing library has a restrictive policy (formats, memory, dimensions) and runs isolated. Owner: `backend`. Source: File Upload.
- **Office documents and archives accepted without structural validation.** Microsoft documents are validated with a document-parsing library, and ZIP files are not recommended because they can contain any file type.
  Check: flag acceptance of archive types; for documents confirm a parse-and-validate step before storage. Owner: `backend`. Source: File Upload.
- **No malware scan or content disarm.** Files are run through an antivirus or sandbox where available, and through Content Disarm & Reconstruct for applicable types (PDF, DOCX).
  Check: confirm the upload pipeline calls a scanner or CDR step and that files are not released until it passes. Owner: `backend`. Source: File Upload.
- **Uploads sent to public scanning services without considering leakage.** Automated review through third-party services (hash lookups, multi-engine scanners) is studied before use, because submitting files can leak data to the service.
  Check: if the pipeline posts files or hashes to an external service, confirm it is approved for the data classification. Owner: `backend`. Source: File Upload.
- **Publicly shared uploads have no abuse path or review.** The service lets users report illegal content and copyright owners report abuse, and where resources allow, files are manually reviewed in a sandbox before public release.
  Check: for public-facing uploads, confirm a report-abuse mechanism and a quarantine or review state before publication. Owner: `backend`. Source: File Upload.
- **Upload parsing libraries outdated or loosely configured.** Every library used to receive or process files is securely configured and kept up to date.
  Check: review the versions and configuration of multipart, image, document, and archive libraries in the manifest. Owner: `dx`. Source: File Upload.

## Access control and request protection

- **Anonymous or unauthorized users can upload.** Uploads require an authenticated or identifiable user so limits can be applied, and authorization checks that the user may access or modify the target files.
  Check: confirm the upload and file-modify routes require authentication and an ownership or permission check on the target object. Owner: `backend`. Source: File Upload.
- **Upload endpoint not protected against CSRF.** File upload is a state-changing request and needs the same CSRF protection as any other.
  Check: confirm the upload route is covered by the CSRF middleware or token check. Owner: `backend`. Source: File Upload.

## Size and resource limits

- **No file size limit, or the limit ignores decompression.** The upload service sets size limits to protect storage; when files are extracted or processed, the limit applies to the decompressed size, computed safely while extracting rather than trusting archive headers.
  Check: confirm a request body and per-file size cap, and that archive extraction streams with a running byte and entry-count limit. Owner: `backend`. Source: File Upload.
- **Download service has no request limits.** Small requests can trigger large responses, so download endpoints have request limits to protect against DoS.
  Check: confirm rate or concurrency limits on file download routes. Owner: `backend`. Source: File Upload.
