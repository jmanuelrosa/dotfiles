# Logging and Error Handling

When to read: the brief, diff, or assessed surface touches log statements, a logging library or log handler, audit or security event logging, error and exception handlers, error responses or problem-details bodies, debug or developer error pages, log shipping, storage, retention, or access, SIEM or alerting rules, or the security events emitted by authentication, authorization, session, upload, admin, or MCP features.

## Sensitive data in logs and error responses

- **Secrets, tokens, or credentials written to logs.** Logs never record passwords, access tokens, raw session ids or bearer tokens, encryption keys and other primary secrets, database connection strings, or application source code; these are removed, masked, hashed, or encrypted (a hashed session id when session correlation is needed), and secrets handling must implement masking or encryption so plaintext secrets are never logged.
  Check: grep new log statements for request headers, cookies, auth objects, config dumps, connection strings, and whole request or user objects; add redaction at the log handler. Owner: `backend`. Source: Logging, Logging Vocabulary, Secrets Management.
- **Sensitive personal or regulated data logged.** Sensitive PII (health, government ids, vulnerable people), payment card and bank data, commercially sensitive data, data above the log system's classification, data illegal to collect, and data the user opted out of or did not consent to are not logged directly; file paths, internal network names and addresses, and non-sensitive personal data (names, phone, email) get special treatment, and de-identification (deletion, scrambling, pseudonymization) is used where identity is not needed.
  Check: flag log fields carrying PII or card data and confirm masking or pseudonymization; flag logging of user IP or email where the event does not need it. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Attack payloads, prompts, or full reports logged verbatim.** Prefer a detection rule id or category plus the parameter name over the full payload (SQLi), strip query strings and fragments from URL-valued CSP report fields and prefer effective directive plus blocked origin and path, log measured usage and request ids rather than full prompts or tool I/O for MCP events, and record deletions by object identifier without copying the deleted contents.
  Check: flag log statements that include raw request bodies, matched payloads, CSP report bodies, or prompt text. Owner: `backend`. Source: Logging Vocabulary.
- **Data logged without legal basis.** Data is never logged unless legally sanctioned (some interception, employee monitoring, and collection without consent can be illegal), and every field after the event type is optional and weighed against data stewardship duties, since even an IP address can be regulated personal data.
  Check: for new security event fields, confirm each is needed for detection or response. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Unhandled errors return stack traces, versions, or queries to the client.** A global error handler catches every unexpected exception, logs the details server side, and returns a generic response that reveals no implementation details (framework or server names and versions, SQL errors, install paths), preferably in the RFC 7807/9457 problem-details format.
  Check: confirm a catch-all handler is registered at the outermost layer and that error bodies contain only a generic message and status; flag `exception.getMessage()` or stack traces placed in responses. Owner: `backend`. Source: Error Handling.
- **Developer exception pages enabled outside development.** Detailed debug or developer error pages are enabled only in the development environment, with the generic global handler active in every other environment.
  Check: read environment-conditional error middleware and server config (for example custom-errors mode) to confirm detailed errors are dev-only. Owner: `backend`. Source: Error Handling.
- **Client and server faults use the wrong status class.** Use 4xx for errors caused by the client (unauthorized access, body too large) and 5xx only for requests the server cannot fulfil because of an unforeseen bug, with failure modes covered exhaustively so 5xx stays meaningful, and monitor the application for 5xx responses.
  Check: confirm validation and authorization failures map to 4xx and that a 5xx rate alert exists. Owner: `backend`. Source: Error Handling.

## Log injection and untrusted event data

- **Event data not sanitized for the log format.** All event data is sanitized against log injection (CR, LF, and delimiter characters) and encoded correctly for the output format; when logs are written to a database, SQL injection defenses apply.
  Check: confirm the logger uses structured fields or encodes user-controlled values, and flag string concatenation of request data into log lines. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Event data from other trust zones trusted or dropped.** Event data from other trust zones (clients, partner systems, browser reports) may be missing, forged, replayed, or malicious and is validated before logging; a malformed field is omitted or safely replaced and the validation failure recorded with bounded context, without discarding the whole security event, and the source's verifiability is considered.
  Check: confirm client-reported events (CSP reports, mobile or JS error beacons) are schema-validated with length limits before logging. Owner: `backend`. Source: Logging.

## Security events that must be logged

Name events with the vocabulary's `<family>_<action>[:arguments]` keys so monitoring can key on the same terms across every application; the families below group the events each feature must emit.

- **Authentication outcomes not logged.** Log every login success and failure (`authn_login_success`, `authn_login_successafterfail` with retries, `authn_login_fail`, `authn_login_fail_max` with the limit), account locks with a reason (`authn_login_lock`: maxretries, suspicious, customer, other), every password change and failed change (`authn_password_change`, `authn_password_change_fail`, CRITICAL), impossible travel (`authn_impossible_travel`), and service token creation with entitlements, revocation, reuse of a revoked token, and deletion (`authn_token_created`, `authn_token_revoked`, `authn_token_reuse`, `authn_token_delete`); failures are key early indicators of brute force, credential stuffing, and password spraying.
  Check: confirm each login, lockout, password-change, and token-lifecycle branch emits its event with the user id, including failure branches. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Authorization and privilege events not logged.** Log access-control failures with user and resource (`authz_fail`), entitlement changes with from and to values (`authz_change`), all activity by administrators and other privileged users (`authz_admin`), and permission changes on access-controlled objects (`privilege_permissions_changed` with from and to levels); also log use of default, shared, or break-glass accounts.
  Check: confirm the central authorization check logs denials and that admin routes and role-change code emit events. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Session lifecycle and anomalies not logged.** Log session management failures (session cookie modification, suspicious JWT validation failures), authenticated session creation, renewal, expiry with a reason (logout, timeout, revoked), explicit logout, and use of an expired session (`session_created`, `session_renewed`, `session_expired`, `session_logout`, `session_use_after_expire`, CRITICAL); revoked sessions are expired rather than deleted, renewals on highly confidential systems may need re-verification, and concurrent-session overruns are logged (`excess_sessions_exceeded`).
  Check: confirm token or cookie validation failures and expired-session access emit events without the raw session id. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Input, output, and probing signals not logged.** Log server-side input validation failures (`input_validation_fail` with fields; `input_validation_discrete_fail` for values outside a fixed option list), output validation failures, deserialization failures, and probing behaviour: excessive 404s (`malicious_excess_404`), unexpected parameters (`malicious_extraneous`), attack-tool signatures (`malicious_attack_tool`), SQLi detections (`malicious_sqli`), disallowed cross-origin requests (`malicious_cors`), direct object reference attempts (`malicious_direct_reference`), CSRF token or origin failures (`malicious_csrf`), CSP violation reports (`malicious_csp_violation`), and requests with unexpected HTTP verbs; treat validation failures as suspicious rather than proof and set severity and alerting from repetition, correlation, and context.
  Check: confirm validation, CSRF, CORS, and object-ownership rejections each emit an event and still block the request. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Business-logic abuse and excessive use not logged.** Log out-of-sequence actions and flow bypasses (`sequence_fail`, CRITICAL), actions that make no sense in the business context, attempts to exceed per-action limits, and service limit ceilings being exceeded (`excess_rate_limit_exceeded`, alerted even for cost and scaling).
  Check: confirm multi-step flows reject and log out-of-order steps and that rate limiters emit an event on rejection. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Sensitive data and user administration not logged.** Log creation, read, update, and deletion of data marked sensitive or held in sensitive stores (`sensitive_create`, `sensitive_read`, `sensitive_update`, `sensitive_delete`) with periodic review, access to sensitive data such as cardholder data, data import and export including screen-based reports, and user creation, update, archive, and deletion with the acting and target user (`user_created`, `user_updated`, `user_archived`, `user_deleted`); archiving users is preferred to deleting them except where deletion is required.
  Check: confirm sensitive-data repositories and user-admin endpoints emit these events with acting user and object id. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **File upload and content events not logged.** Log submission and processing of user content, especially uploads: completion (`upload_complete`), the move or rename to storage (`upload_stored`), each validation step with its result (`upload_validation` such as virus scan or image processor passed, incomplete, FAILED), deletion (`upload_delete`), and virus detections.
  Check: confirm the upload pipeline emits an event per stage and that scanner failures are logged as FAILED. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Cryptographic and connection failures not logged.** Log encryption and decryption failures (`crypt_encrypt_fail`, `crypt_decrypt_fail`), use or rotation of cryptographic keys, network connection failures including backend TLS and certificate validation failures, third-party service errors, and file system errors.
  Check: confirm crypto and outbound-client error paths log an event rather than swallowing the exception. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **System and monitoring lifecycle not logged.** Log startup, shutdown, restart, and crash of the application and related systems (including serverless and containers) with the initiating user where possible (`sys_startup`, `sys_shutdown`, `sys_restart`, `sys_crash`), logging initialization, stop, or pause, configuration changes, creation and deletion of system-level objects, and disabling or re-enabling of integrity, logging, or antivirus monitors with who did it (`sys_monitor_disabled`, `sys_monitor_enabled`).
  Check: confirm startup and shutdown hooks and config-change paths emit events. Owner: `sre`. Source: Logging, Logging Vocabulary.
- **MCP abuse signals not logged.** MCP clients and servers block or constrain and log prompt injection indicators (`mcp_prompt_injection`), throttle and log resource exhaustion such as oversized prompts or tool-call loops (`mcp_resource_exhaustion`), and quarantine and log suspected tool poisoning such as unexpected tool changes or hash verification failures (`mcp_tool_poisoning`); an internal marketplace or hashed allowlist of approved tools is highly recommended.
  Check: confirm MCP gateway or client code emits these events with a rule id, tool or server, and request id. Owner: `backend`. Source: Logging Vocabulary.
- **Consent and legal opt-ins not logged.** Log legal and other opt-ins: mobile capability permissions, terms of use acceptance, personal data usage consent, and marketing permission.
  Check: confirm consent changes emit an event with the user and version accepted. Owner: `backend`. Source: Logging.
- **Events from known or trusted actors excluded.** Events from internal systems, trusted third parties, search robots, uptime monitors, pen testers, and auditors are never excluded; a classification flag identifies them instead.
  Check: flag log filters that drop events by user agent, IP allowlist, or service identity. Owner: `backend`. Source: Logging.

## Log protection, storage, and availability

- **Logs readable or writable beyond need.** Log mechanisms and data are protected against tampering in transit and unauthorized access, modification, and deletion at rest: build in tamper detection, copy to read-only media as soon as possible, record and monitor all access to logs, and restrict and periodically review read privileges.
  Check: confirm the log store has write-once or append-only settings, access logging, and a narrow reader role. Owner: `sre`. Source: Logging.
- **Log files exposed through the web or shared storage.** File-based logs use a separate partition from the OS, application files, and user content, with strict directory and file permissions, and are never in web-accessible locations (if unavoidable, access-restricted and served as plain text, not HTML); database logging uses a dedicated write-only account with very restrictive permissions.
  Check: confirm log paths are outside the document root and that the log-writing DB user cannot read or alter other tables. Owner: `backend`. Source: Logging.
- **Logs shipped without a secure transport.** Logs use a standard format and secure transport (for example syslog RFC 5424 over TLS per RFC 5425) to a centralized collector, log data crossing untrusted networks uses a secure protocol, event origin is verified where needed, and regulatory and security due diligence precedes sending events to third parties.
  Check: confirm the log shipper's endpoint uses TLS and that third-party log destinations are approved. Owner: `sre`. Source: Logging.
- **Logging failure breaks the app or enables DoS.** Logging failures must not stop the application or leak information, logging cannot exhaust disk or database transaction space, and if log data drives actions against users (blocking, lockout), it cannot be abused to deny service to other users.
  Check: confirm the logger is non-blocking or fails open with bounded buffers, log volumes have rotation and quotas, and lockout logic keys on the right identity. Owner: `backend`. Source: Logging.
- **Logging can be switched off or silently stops.** Adjustable logging keeps a default level sufficient for business needs, cannot fully deactivate logging or compliance-required events, changes levels only through an approved algorithm or change management, and is verified periodically; processes detect when logging has stopped and flag tampering, unauthorized access, or deletion.
  Check: flag config or admin endpoints that can disable security logging, and confirm an alert on missing log flow per service. Owner: `sre`. Source: Logging.
- **Security, audit, and debug data mixed.** Security event logs are kept separate from process-monitoring, audit, and transaction trails collected for other purposes, and extended details (stack traces, HTTP headers and bodies) go to separate files or tables.
  Check: confirm security events go to a distinct stream or carry a security flag, and verbose request dumps are not in the main security log. Owner: `backend`. Source: Logging.

## Event format and naming

- **Events missing when, where, who, and what.** Every entry records when (log time and event time in ISO 8601 with UTC offset, interaction or correlation id), where (application id and version, host or address and port, service and protocol, entry point URL and HTTP method, code location), who (source address, user identity), and what (event type, severity, security flag, description); consider also action, object, result status, reason, HTTP status, user agent, user type classification, detection confidence, and the response taken.
  Check: compare the logger's base fields with this list (the vocabulary's example uses `datetime`, `appid`, `event`, `level`, `description`, `useragent`, `source_ip`, `host_ip`, `hostname`, `protocol`, `port`, `request_uri`, `request_method`, `region`, `geo`); flag timestamps without offset and missing correlation ids. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Event names and severities invented per feature.** The organization documents one approach to event classification (type, confidence, severity), description syntax, field lengths, and data types, and applies the vocabulary's keys and levels consistently (INFO for success, WARN for failures and suspicious input, CRITICAL for probing, sequence failures, password-change failures, and use of expired sessions).
  Check: flag new security events whose names do not follow `<family>_<action>` or whose level contradicts the vocabulary. Owner: `backend`. Source: Logging, Logging Vocabulary.
- **Each module logs security events its own way.** Use the framework's logging mechanism or one application-wide log handler with a documented interface, ideally a tested reusable module approved for multiple applications, emitting a standard or exportable format.
  Check: flag direct prints or ad hoc file writes for security events instead of the shared handler. Owner: `backend`. Source: Logging.
- **Clocks unsynchronized across event sources.** Time is synchronized across all servers and devices; where the device is outside your control, measure the offset or record timestamp confidence.
  Check: confirm hosts and containers use time sync and client-originated events carry both client and server time. Owner: `sre`. Source: Logging.

## Monitoring, retention, and verification

- **Security events collected but nobody alerted.** Application logs feed centralized log management, are available to the right teams, raise immediate alerts for serious events, integrate with incident response, and share relevant signals with other detection systems; repeated failures per account, failures from many IPs, and bursts of attempts are monitored.
  Check: confirm alert rules exist for the CRITICAL vocabulary events and authentication failure patterns, with an IR destination. Owner: `sre`. Source: Logging, Logging Vocabulary.
- **Logging scope not set at design time.** The level and content of security monitoring, alerting, and reporting are set during requirements and design in proportion to risk, using threat modeling of what could go wrong, rather than a blind checklist that creates alarm fog.
  Check: confirm the design or threat model names the security events a feature must emit. Owner: `architect`. Source: Logging, Logging Vocabulary.
- **Logs kept too short or too long.** Log data, temporary debug logs, and backups or extracts are kept for the required retention period and not beyond it, per legal, regulatory, and contractual obligations.
  Check: confirm retention and lifecycle settings on log stores match the documented period. Owner: `sre`. Source: Logging.
- **Logging untested.** Logging is part of code review and testing: verify it works as specified, classification and field definitions are consistent, it is enabled during security, fuzz, penetration, and performance tests, it resists injection, it behaves under connectivity loss, full disk, missing permissions, and logger runtime errors, and access controls on log data hold.
  Check: confirm tests assert that security events are emitted on failure paths and that CR/LF in input does not split log lines. Owner: `qa`. Source: Logging.
- **Logging undocumented at release.** Release documentation describes the logging mechanisms and security configuration, and the application owner is briefed.
  Check: confirm the service's operational docs list its security events and log destinations. Owner: `sre`. Source: Logging.
