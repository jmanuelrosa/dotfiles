# Privacy and Payments

When to read: the brief, diff, or assessed surface touches checkout, cart totals, a third-party payment gateway, payment return URLs or payment webhooks, AI agents initiating payments, sanctions or AML screening, compliance receipts and audit trails, or user privacy features (session lists, panic modes, anonymity-network access, third-party embedded content, transparency about data requests).
Sources (OWASP Cheat Sheet Series, CC BY-SA 4.0): [User Privacy Protection](https://cheatsheetseries.owasp.org/cheatsheets/User_Privacy_Protection_Cheat_Sheet.html), [Secure Integration of Third-Party Payment Gateways](https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Payment_Gateway_Integration_Cheat_Sheet.html), [AML and Sanctions Compliance for AI Agent Payments](https://cheatsheetseries.owasp.org/cheatsheets/AML_Sanctions_AI_Agent_Payments_Cheat_Sheet.html)

## Payment gateway flow integrity

- **Cart totals trusted from the client.** Validate every cart detail (product IDs, prices, discounts) on the backend and recalculate totals server-side from trusted data before creating the gateway order; otherwise the client can tamper with prices or substitute products.
  Check: the order-creation handler reads prices from the catalog and computes the total itself, ignoring any amount or price sent by the client. Owner: `backend`. Source: Payment Gateway.
- **Order fulfilled from the browser return redirect.** User redirection parameters are untrusted; only server-to-server callbacks are trusted for payment verification and fulfillment, and the payment status is always verified server-side with the gateway's API before fulfilling, matching the expected amount, currency, and order ID.
  Check: the return-URL handler never marks an order paid, and fulfillment runs only after a gateway API lookup whose amount, currency, and order ID are compared with the stored order. Owner: `backend`. Source: Payment Gateway.
- **Payment callback accepted without authenticity check.** Validate every gateway callback's authenticity (for example HMAC signatures or secret tokens) before acting on it, since spoofed callbacks otherwise mark unpaid orders as paid.
  Check: the callback handler verifies the signature before parsing the body into business actions and rejects on failure. Owner: `backend`. Source: Payment Gateway. See `rest-and-webhooks.md` for webhook signature verification.
- **Callback processed more than once.** Fulfillment is idempotent: an order is processed once regardless of how many times or how concurrently its callback arrives, backed by persistent duplicate-event records, so replays cannot trigger repeated shipments or account credits.
  Check: fulfillment is guarded by a unique constraint or atomic state transition on the order or event ID, not an in-memory check. Owner: `backend`. Source: Payment Gateway.
- **Late or out-of-order notification discarded.** Checkout expiry is handled separately from webhook signature freshness: gateways retry and reorder events, so late notifications are verified and reconciled against the current payment state rather than discarded solely because the checkout expired.
  Check: the handler for an expired checkout still verifies and reconciles a valid late payment event (refund or fulfill) instead of dropping it. Owner: `backend`. Source: Payment Gateway.

## Payment logging and monitoring

- **Payment logs hold raw requests or card data.** Log every payment attempt (initiation, redirects, callbacks) with timestamps and IPs, recording callback identifiers, validation outcomes, and order correlation data instead of raw headers and bodies; exclude credentials and unnecessary personal or payment data, never retain sensitive authentication data such as card verification codes or PIN data after authorization even if encrypted, and restrict access to and define retention of investigation records.
  Check: payment logging writes named fields only, and no code path persists CVV or PIN data. Owner: `backend`. Source: Payment Gateway.
- **No payment anomaly alerting.** Alert on orders marked paid without gateway confirmation, excessive callback attempts for one order, and payment failures followed by repeated attempts with identical data, and add fraud and risk scoring to detect carding during payment execution.
  Check: alert rules for these three conditions exist and a risk-scoring step sits in the payment path. Owner: `sre`. Source: Payment Gateway.

## Agent payments: identity and trust

- **Agent credential treated as the legal customer or as compliance.** Separate legal customer and counterparty identification from software authentication and authorization, record which customer an agent acts for and what it may do, and have compliance owners define screening, monitoring, reporting, and retention per institution, transaction, relationship, and jurisdiction; an agent credential or a clean list check never proves the legal obligations are met, and a cross-border system never relies on a single jurisdiction's lists or rules.
  Check: the design binds each agent to a verified account and its delegated permissions, with compliance-owned rules referenced rather than hardcoded assumptions. Owner: `architect`. Source: AML Agent Payments.
- **Self-declared agent identity accepted.** Before an agent reaches screening or initiates a payment, its identity is cryptographically verified (signed passport, ECDSA key pair, or verifiable credential); self-declared headers such as `X-Agent-ID` or `X-Agent-Role` MUST be rejected, anonymous agents MUST NOT access screening, authorization is validated on every request (following the MCP authorization profile for MCP endpoints), and caller-supplied identity headers are never trusted just because TLS terminates at a proxy: a validated client-certificate identity is accepted only over a trusted proxy path that strips caller-supplied certificate headers.
  Check: the screening and payment handlers derive agent identity from a verified credential, and the proxy config removes inbound certificate-identity headers. Owner: `backend`. Source: AML Agent Payments.
- **Agent able to raise its own trust level.** Use graduated trust levels (for example L0 to L4) with increasing access rights, verify the level before granting access, never let an agent escalate its own trust or modify its own permissions, and do not treat a one-time identity check as sufficient for ongoing access.
  Check: trust level is read from server-side state the agent cannot write, and no agent-callable endpoint changes it. Owner: `backend`. Source: AML Agent Payments.
- **Agent operator unidentified or never rescreened.** Verify the organization responsible for each agent at onboarding independently against business registries or KYB data, screen the parties the compliance program identifies, define rescreening triggers and frequency (including list and ownership changes), restrict access when the relationship may not continue, record the operator's screening status in the agent's trust profile, and require the operator identity inside the agent's credential; agents without a declared operator are not allowed.
  Check: agent registration requires a verified operator reference and a rescreen job exists. Owner: `backend`. Source: AML Agent Payments.
- **Agent rate limits keyed on IP address.** Rate limit per cryptographic agent identity rather than IP, with lower limits for new or low-trust agents (L0/L1) and higher for verified high-trust ones (L3/L4), return remaining quota and reset time, downgrade allocations on anomalous behavior, keep limits low enough to matter, and tie identities to verified operator accounts so multiple identities cannot evade limits.
  Check: the rate-limit key is the agent key fingerprint or passport ID and limits vary by trust tier. Owner: `backend`. Source: AML Agent Payments.

## Agent payments: sanctions screening

- **Payment reachable without prior screening.** Screen all counterparties (individuals, businesses, vessels, addresses) against the applicable sanctions lists (OFAC SDN, UK Sanctions List, EU Consolidated, UN Consolidated) before processing a payment, and never let agents call payment endpoints directly without the screening step.
  Check: the payment-execution path requires a valid screening result for the transaction and has no route that skips it. Owner: `backend`. Source: AML Agent Payments.
- **Screening fails open.** An incomplete, unavailable, ambiguous, or timed-out screen is unresolved, never clearance: hold or reject the payment, never add fallback logic that bypasses screening under any condition, use bounded retries, manual review, or rejection per approved policy, return a structured error that distinguishes "screening unavailable" from "match", log failures as fully as successes, rate limit retries, and add circuit breakers that halt agent-initiated payments during extended screening outages.
  Check: every error and timeout branch of the screening client leads to hold or reject, and error responses carry distinct codes for unavailable versus match. Owner: `backend`. Source: AML Agent Payments.
- **Agent can lower match thresholds or override results.** Enforce the institution's configured minimum match threshold and never let an agent lower it or override a screening result.
  Check: the threshold comes from server configuration, not request parameters. Owner: `backend`. Source: AML Agent Payments.
- **Stale or raw screening data in agent hands.** Agents may not cache screening results beyond a configurable window, never receive raw sanctions list data (they call a screening API), and get structured JSON results with match, no-match, or partial-match indicators and scores; the screening context includes the agent's identity and trust level so downstream systems can tell agent-initiated screens apart.
  Check: screening responses carry an expiry the payment path enforces, and no endpoint returns list contents. Owner: `backend`. Source: AML Agent Payments.
- **Screening failure spikes unmonitored.** Alert compliance teams when screening failure rates exceed a threshold, since a deliberate DoS may aim to force fail-open behavior.
  Check: an alert rule on screening failure rate exists. Owner: `sre`. Source: AML Agent Payments.
- **Hosted screening receives more than it needs.** Encrypt all screening requests in transit with TLS 1.2 at minimum, send a third-party provider only the minimum identity attributes and data (never agent private keys or full credentials), ensure the provider meets applicable regulatory requirements, and protect each connection after TLS termination by deciding which intermediaries may read or modify requests; where untrusted intermediaries are in the threat model, use a reviewed message-signing profile with defined trusted keys, signed fields, replay handling, and failure behavior, and verify provider response signatures when the profile requires them.
  Check: the provider request builder sends an explicit minimal field set and the client enforces TLS 1.2 or higher. Owner: `backend`. Source: AML Agent Payments.

## Agent payments: audit trail and receipts

- **Screening audit trail mutable or agent-held.** Keep tamper-evident audit records, on institution-controlled infrastructure and never on agent devices or agent-controlled storage, that associate the authenticated agent (key fingerprint or passport ID) with the tool invoked, a hash of the screening arguments rather than raw arguments, the result, a timestamp, and a unique nonce; application logs alone are not an audit trail. In a hash-chained design each entry includes the SHA-256 hash of the previous one and any chain gap triggers an alert. Retain records for the regulatory period (typically 5 years for BSA/AML) and make them exportable in a machine-readable format.
  Check: audit writes go to an append-only, institution-owned store with the listed fields and retention set. Owner: `backend`. Source: AML Agent Payments.
- **Signed screening messages not verified.** When a message-signing profile is in use, sign each screening request with the agent's key and each response with the server's key, each with its own nonce and timestamp, enforce the profile's replay controls, and reject unsigned or invalidly signed results the profile requires to be signed; TLS does not stop a compromised component from altering data after termination.
  Check: signature and nonce verification run before a screening result is accepted, and failures reject. Owner: `backend`. Source: AML Agent Payments.
- **Compliance receipt not verified at each hop.** Attach the signed compliance receipt to the transaction, sign over the transaction or intent hash, and propagate it across every agent hop; each hop verifies signature, trusted issuer, transaction binding, and acceptable screening freshness before relying on it and appends its own signed receipt for any action it takes. A signature proves origin and integrity, not that screening was done correctly, so verifiers keep a policy of trusted screening issuers; receipts kept only in the issuer's logs, or upstream claims that cannot be verified, are not relied upon.
  Check: downstream handlers verify the inbound receipt against an issuer allowlist and the current transaction hash before acting. Owner: `backend`. Source: AML Agent Payments.
- **Receipt missing sanctions-list version and freshness.** Put the list source(s), version or publication date, and screening timestamp inside the signed receipt bound to the specific transaction, enforce the verifier's own maximum list and screening age (never an issuer-supplied limit), and retain evidence of the list version used and the screening service's update history; "screened" is not a boolean.
  Check: receipt schema includes list version and timestamp fields and the verifier compares them with its configured maximum age. Owner: `backend`. Source: AML Agent Payments.
- **Signed JSON re-serialized with default serialization.** When the receipt profile requires independently serializing JSON, canonicalize the agreed payload (RFC 8785 JCS) before signing and before verifying rather than relying on framework-default or pretty-printed output, use exactly the hashing and signing procedure the profile requires (no extra prehash unless it says so), and record the canonicalization and signature profile used; a JWS verifier checks the encoded signing input and does not need JCS.
  Check: signing and verification paths call the same canonicalizer and record the profile identifier. Owner: `backend`. Source: AML Agent Payments.

## User privacy protection

- **Private data or communications weakly protected.** Platforms handling identities, private information, or communications must encrypt communications in transit and in storage, encrypt private data at rest with sufficiently long keys under strict technical and procedural access, and hash user credentials with strong algorithms and increasing work factors regardless of whether they are also encrypted; TLS uses verified certificates, protected private keys, strong ciphers only, sufficient key lengths, and clear warnings to users.
  Check: private-message and profile storage is encrypted, and credential storage uses an adaptive password hash. Owner: `backend`. Source: User Privacy. See `cryptography-and-keys.md` and `authentication.md` for algorithms and parameters.
- **HSTS neither enforced nor offered.** Set HSTS so user agents accept only HTTPS; where forcing it on all users is impractical, at least let users opt in.
  Check: responses carry `Strict-Transport-Security`. Owner: `backend`. Source: User Privacy. See `http-headers-tls-and-caching.md` for HSTS values.
- **No way to see and revoke active sessions.** Let users view their current sessions and invalidate suspicious ones, for lost, stolen, or confiscated devices and suspected cookie theft.
  Check: a session-list endpoint and a per-session revoke action exist. Owner: `backend`. Source: User Privacy. See `sessions-and-cookies.md` for session invalidation.
- **Panic mode detectable by an adversary.** Where threatened users are in scope, a panic mode (delete data, decoy account or inbox, hide sensitive data) must not be easily discoverable: normal non-sensitive operations keep working inside it, further panic modes can be created from inside it or panic modes are created only out of band, and nothing reveals that one exists or lets the adversary reach the real account.
  Check: panic-mode sessions return the same UI and API shape as real sessions and expose no flag or setting that reveals the mode. Owner: `architect`. Source: User Privacy.
- **Anonymity networks blocked by default.** Pursue every avenue to let users reach the service through anonymity networks such as Tor, carefully re-evaluate any policy against them, and where possible support SOCKS proxies or integration libraries.
  Check: WAF or edge rules do not block Tor exit nodes without a documented re-evaluation. Owner: `cloud`. Source: User Privacy.
- **Embedded third-party content leaks user IP addresses.** Applications that render external content (avatars, signatures, embedded images, HTML email) consider letting users block third-party content, since an attacker hosting an embedded image learns the viewer's IP.
  Check: user-supplied external images are proxied or blockable via a user setting. Owner: `frontend`. Source: User Privacy.
- **Users not told about protection limits or data requests.** When the application cannot provide enough legal or political protection or cannot prevent misuse or disclosure of sensitive information such as logs, it says so clearly, and where lawful it informs users when external entities request removal or investigation of their information.
  Check: the privacy policy and notification flows cover these disclosures. Owner: `architect`. Source: User Privacy.
